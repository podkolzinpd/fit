# Учётка и связь в FIT

Начинай с [проверенных маршрутов](references/verified-routes.md), а не с нового
скрипта, PR, сервиса, SSH-подключения или запроса данных у человека.
Это инструкция выбора и исполнения существующих операторов, не новый оператор.

1. Найди настоящий checkout `podkolzinpd/fit` по проектному AGENTS; проверь Git
   root, ветку, чужие изменения и свежий main. Читай AGENTS, FIT_WORKFLOW,
   CURRENT_STATE и ACTIVE_CONTRACTS из актуальной основы. Не занимай чужую ветку.
2. Прочитай относящийся к задаче private checkpoint, operator state и закрытый
   readback **внутри локального процесса**, выводя только необходимые безопасные
   выводы. Сначала установи, что уже проверено, что разрешено и какой последний
   запуск завершён. Не повторяй завершённый поиск без изменившегося входа/факта.
3. Выбери готовую ветку из таблицы в reference: адрес/login → account-links;
   список клиентов → roster; существующее доказательство текущего профиля →
   account-history; подтверждённая пара/карточка → существующий repair operator.
   Импорт журналов не повторяется ради восстановления связи.
4. До запуска сверяй реальную схему input и возможности оператора в trusted
   main. Подготовка в PR не означает, что функция выпущена или учётка найдена.
   Для готового оператора используй код принятого main/проверенный snapshot;
   невыпущенные изменения в HEAD не должны подменять его или требовать новый выпуск.
   Используй уже имеющееся доказательство; не проси ту же почту, имя, ссылку
   или новое обращение, пока не проверены доступные сохранённые сведения.
5. Разрешение на чтение не открывает запись. Перед ремонтом нужны точная
   текущая identity/роль, каноническая карточка и история, отсутствие конфликтов,
   штатный backup/restore proof, свежий план и все guards выбранного оператора.
   Существующий userId, Yandex identity, роли и пилоты не переназначаются по догадке.
6. Неопределённый исход внешней записи сначала сверяй по сохранённому run и
   закрытой квитанции/verify. Не повторяй apply и не обходи TTL. После ремонта
   отдельно проверь доступ **обоих** пользователей и сохранность истории/финансов;
   затем штатный cleanup только своих временных ресурсов.

## Обязательные границы

- Email не хранится в native-профилях. Пустой lookup означает «не разрешён этим
  источником», а не «учётки нет». Yandex identity=0 не доказывает вторую учётку.
  Говори «известный профиль» и «текущий профиль не подтверждён», пока связь не доказана.
- Одно имя, одноимённая карточка или наличие сеанса не выбирают actor.
  Не создавай аккаунт и не меняй роль для обхода неопределённости.
- Контакты, native IDs, hashes/evidence/payload/readbacks и секреты не попадают
  в code, отчёты, automation или tool/model text. Значения — private files0600,
  stdin/memory. Производные hashes тоже являются данными; egress в GitHub
  разрешён только в явно согласованном объёме. Чужие secrets не перезаписывать.
- При запрете GitHub используй существующий private local↔Cloud.ru канал.
  Его наличие не означает поддержку произвольного SQL/новой операции.
  Реальный пробел доказывай точным отсутствующим input/query/guard в существующем
  операторе; только тогда минимальный reviewed fix в нём, без нового транспорта.
- Не создавай чаты, cron или монитор ради продолжения этой задачи. Не отправляй
  сообщения другим чатам без разрешения. Очередь и правила выпуска сохраняются;
  чужой возраст/единичный сбой не являются разрешением обхода.
- Сообщай проверенный результат или действительно недостающий шаг человека.
  CI/PR/подготовку не выдавай за найденный профиль или восстановленную связь.
- Отказ автоматической проверки разрешений не обходи другим клиентом или
  источником. Закончи независимую часть и назови отклонённый доступ и его причину.

Сценарии для проверки изменения инструкции: [evals/cases.json](evals/cases.json).
