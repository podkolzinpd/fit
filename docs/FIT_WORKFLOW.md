# Fit — компактный процесс работы

Цель этого файла — дать новой сессии достаточно контекста без загрузки всей
истории проекта. По умолчанию читайте только `AGENTS.md`, этот файл,
`docs/CURRENT_STATE.md` и материалы, которые относятся к текущей задаче.

Этот файл хранит только стабильный процесс. Изменяемое состояние проекта живёт
в коротком `docs/CURRENT_STATE.md`, чтобы рост проекта и количества сессий не
увеличивал стартовый контекст.

## Источники правды

При расхождении используйте порядок:

1. Последняя формулировка и подтверждённые решения пользователя.
2. Актуальный `main`: код, миграции и тесты.
3. Тикет YAFIT и его комментарии.
4. `docs/CURRENT_STATE.md` — короткий индекс последней проверенной точки; его
   факты нужно сверять с `main` и Tracker.
5. Релевантный раздел `docs/PRODUCT_WIKI.md` — реализованный продукт.
6. `docs/design/` и `FEATURE_PARITY.md` — планы и V1 baseline.
7. Старые handoff и память — контекст, который нужно перепроверить.

Документ, CSS-класс или зелёный тест сами по себе не доказывают, что экран и
поведение актуальны. Сверяйте спорное с кодом, реальным экраном и Tracker.

## Экономный старт сессии

1. Прочитать `AGENTS.md`, этот файл и `docs/CURRENT_STATE.md`.
2. Проверить `git status`, ветку, `main`, открытый PR и YAFIT-тикет.
3. По ключевым словам найти нужные разделы: сначала заголовки через `rg -n '^#'`,
   затем читать только подходящие диапазоны строк.
4. Воспроизвести исходное состояние; для UI сохранить baseline на 390 px.
5. Сформулировать один пользовательский результат и границы задачи.

### Preflight новой worktree

До первой дорогой проверки убедитесь, что в worktree доступны уже закреплённые
зависимости, локальный Supabase через Podman и нужный браузер. Не обнаруживайте
отсутствующие `supabase`, Playwright или ESLint посреди `db reset`, e2e или CI.
Если `package-lock.json` совпадает с уже подготовленной worktree, переиспользуйте
её `node_modules` и сначала проверьте версии инструментов; не запускайте новый
`npm ci` без изменения lock-файла или фактической несовместимости зависимостей.
Перед новым e2e-файлом проверьте ограничения ESLint/tsconfig; если лимит на
default project исчерпан, расширяйте существующий релевантный spec, а не
ослабляйте линтер ради одной задачи.

Не читать целиком всю документацию «на всякий случай»:

- `ARCHITECTURE.md` — когда меняются границы слоёв, состояние, БД или realtime;
- `docs/PRODUCT_WIKI.md` — только раздел затронутого сценария;
- `FEATURE_PARITY.md` — только для parity-задачи;
- `docs/design/` — только файл, связанный с тикетом;
- `README.md` и `docs/AI_AGENT_ONBOARDING.md` — при настройке окружения;
- историю прошлых сессий — только если короткого handoff недостаточно.

Если checkout в detached HEAD, создать рабочую ветку от актуального `main` до
коммита. Не затирать чужие незакоммиченные изменения.

## Цикл одной задачи

Одна проблема = один тикет, одна ветка, один PR.

1. Воспроизвести и определить acceptance cases.
2. Найти путь UI → feature → repository → query → DB только настолько глубоко,
   насколько требует причина.
3. Реализовать минимальный scope без соседнего редизайна и рефакторинга.
4. Для мутирующего e2e сначала собрать полную fixture всех проходимых шагов и
   запустить один целевой сценарий последовательно (`workers=1`). Красный тест
   сначала диагностировать в порядке fixture → селектор/ожидание → ответ API →
   продуктовый дефект; не менять продуктовый код по первому падению.
5. Запустить сначала целевые тесты, затем проверки по риску. Полный `npm run
   check` запускайте один раз после стабилизации diff, не повторяйте без нового
   сигнала.
6. Для UI проверить реальный WebKit-экран на 390 px: длинный текст, клавиатуру,
   safe-area, loading/empty/error/success и сценарий назад.
7. Просмотреть diff, выполнить `git diff --check` и убрать случайные файлы.
8. Обновить только нужный источник: реализованное — `PRODUCT_WIKI`, план —
   `docs/design`, живой статус — Tracker. Если нужен rolling snapshot, обновить
   `CURRENT_STATE.md` в этой же ветке; не выносить его в отдельный служебный PR.
9. Открыть PR с результатом, тикетом, проверками, скриншотом и ограничениями.
   Передавайте текст описания в GitHub CLI без shell-интерполяции Markdown-кода.
   По умолчанию передать PR пользователю. Если пользователь явно разрешил
   автономное завершение, дождаться CI, прочитать причину каждого падения,
   слить только зелёный PR и проверить production самостоятельно.
10. После merge сверить snapshot с фактом. Второй docs-only PR создавать только
    когда после merge появилась новая существенная фактура, которую нельзя было
    корректно зафиксировать в продуктовом PR. Следующую задачу не начинать без
    отдельной команды пользователя.

Найденную соседнюю проблему записать отдельно и не расширять текущий PR.

## Проверки по риску

- Документация: ссылки, смысловая проверка и `git diff --check`.
- TS/UI: целевой unit/component test, lint и typecheck; перед PR с кодом —
  `npm run check`, если нет зафиксированного внешнего блокера.
- Пользовательский сценарий: релевантный E2E; не гонять полный набор повторно без
  причины.
- БД/RLS: migration, `npm run db:reset`, `npm run db:test`, generated types.
- iOS: после merge синхронизировать новый `main`, собрать, установить и запустить
  свежий bundle; старый симулятор не считается проверкой. Xcode не открывать
  повторно: если окно Fit уже есть, достаточно build/install/launch; открыть
  проект можно только когда Xcode ещё не запущен или нужна отдельная отладка.

До подтверждённого merge не выдавать iOS sync/build/install за проверку нового
`main`. Подготовительные локальные проверки ветки допустимы, но финальный iOS
bundle после merge должен быть синхронизирован, собран, установлен и запущен из
нового `main`.

Не перезапускать CI вслепую: сначала прочитать точный job/log и отделить баг,
устаревшее ожидание, flaky, тестовые данные и инфраструктуру.

## Неподвижные границы

- UI-правка не меняет prompt, matching, fallback или сохранение LLM-разбора без
  отдельного продуктового решения.
- Локальная разработка использует локальный Supabase. Не читать и не печатать
  `.env.local`, не менять production-данные и секреты.
- Не переименовывать тексты и селекторы без необходимости: на них могут
  опираться E2E.
- После merge закрыть YAFIT, обновить сводный backlog и при необходимости
  пересобрать iOS-приложение.

## Коммуникация и handoff

Во время долгой работы давать короткий статус после значимого этапа или примерно
раз в минуту. Сообщать результат проверки, а не поток команд.

Handoff должен быть коротким:

```text
main/commit; ветка/PR; YAFIT;
что сделано; что проверено; что не проверено;
следующая одна задача; состояние дерева; нужен ли новый iOS bundle.
```

## Автоматическое управление контекстом

Агент сам поддерживает компактность работы; пользователь не должен вручную
пересказывать историю или напоминать об оптимизации.

- `docs/FIT_WORKFLOW.md` не хранит хронологию и не растёт после каждого PR.
- `docs/CURRENT_STATE.md` — rolling snapshot максимум на 120 строк. После merge
  разделы заменяются, а не дописываются в конец.
- В snapshot остаются только: проверенный `main`, активная задача, последние
  значимые изменения, фактические проверки, открытые блокеры и ближайшие
  приоритеты. Полная история остаётся в Git и Tracker.
- Новая сессия не читает весь Git log, все тикеты и всю документацию. Сначала
  загружаются три обязательных файла, затем — только разделы текущего сценария.
- Поиск выполняется точечно через `rg`; длинные логи и CI-вывод сводятся к
  причине сбоя и релевантному фрагменту.
- Одна сессия по возможности ведёт один PR. Snapshot обновляется в этом же PR,
  если нужная фактура уже известна; после merge агент готовит короткий handoff,
  прежде чем брать следующую задачу.
- Полный аудит проекта повторяется только по явному запросу или при
  противоречии между кодом, Tracker и snapshot.

Если `CURRENT_STATE.md` расходится с `main`, агент исправляет snapshot в рамках
текущей документационной или продуктовой ветки и продолжает от проверенного
состояния. Просить пользователя восстанавливать контекст не нужно.
