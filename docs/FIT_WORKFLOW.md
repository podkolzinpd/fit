# Fit — карта контекста и записей

Основные правила работы — только [AGENTS.md](../AGENTS.md), основанный на новом
документе владельца. Этот файл адаптирует его пункты 1 и 6 к существующему
хранению знаний Fit. Это не второй процесс разработки/выпуска и не новый журнал.

## Где брать контекст (пункт 1)

| Источник | Содержание / когда читать |
| --- | --- |
| [CURRENT_STATE](CURRENT_STATE.md) | Короткая актуальная точка продолжения, активные задачи и ссылки |
| [ACTIVE_CONTRACTS](ACTIVE_CONTRACTS.md) | Весь компактный индекс; затем действующие решения затрагиваемой области |
| [PRODUCT_WIKI](PRODUCT_WIKI.md) | Реализованный продукт, соответствующий раздел |
| docs/design и канонический план задачи | Принятые SVG/handoff, требования, ID, причины и последние этапы задачи |
| [REGRESSION_LESSONS](REGRESSION_LESSONS.md) | Повторные ошибки и необходимые проверки своей области |
| [ARCHITECTURE](../ARCHITECTURE.md), [ENGINEERING_RULES](ENGINEERING_RULES.md), [playbook](YANDEX_CUTOVER_PLAYBOOK.md) | Конкретная архитектура, права, миграции, зависимости и технические команды по области |
| [UI_IDENTITY](UI_IDENTITY.md), [UI_TASK_PROMPT](UI_TASK_PROMPT.md), [UI_DESIGN_SYSTEM](UI_DESIGN_SYSTEM.md) | Принятый визуальный контракт, компоненты и параметры UI-проверки |

Порядок приоритета: последнее подтверждённое решение и границы разрешения →
действующие решения/канонический план/принятые источники → фактические код и
сборка как свидетельства реализации. Wiki описывает продукт, тикет — статус;
история объясняет причины. Наличие в коде не означает согласованность.

В зеркале проекта sources/ и сгенерированные инструкции не редактируются.
Сначала найти Git checkout и прочитать его основной документ. Корпоративная KB
не заменяет контекст Fit; при её сбое использовать этот репозиторий, не чинить
чужую базу ради задачи Fit.

## Куда записывать результат (пункт 6)

| Что | Единственное основное место |
| --- | --- |
| Исходный план, результаты этапов, проверки/непроверенное, открытое и следующий шаг | Канонический план задачи: существующий документ либо тикет; PR ссылается на него |
| Существенное решение: ID, причина, отвергнутые варианты, область действия и замена | Документ соответствующей области; ссылка из ACTIVE_CONTRACTS |
| Повторная ошибка, причина и необходимая защита | REGRESSION_LESSONS, только существенная новая находка |
| Текущая точка продолжения | CURRENT_STATE, короткая сводка со ссылками |
| Фактический статус задачи / итог PR | Tracker / PR; не отдельная полная копия журнала |

На завершённый логический этап — запись по составу §6 AGENTS. Существующую
запись не дублировать в других местах: достаточно ссылки и краткого статуса.
Утверждённые пункты сохраняют ID и смысл; изменение решения фиксируется как
замена, а не молчаливое удаление. При исправлении неверного исторического
утверждения добавить связанное уточнение. Актуальную таблицу статусов можно
обновлять; исходная история и причины сохраняются.

CURRENT_STATE ограничен 12 KiB,120 строками и600байтами на строку. Здесь не
накапливаются записи CI. Завершённые материалы остаются доступными по ссылкам;
неясное требование не объявляется отменённым или выполненным при переносе.
Контакты, UUID пользователей, приватные записи экрана и секреты не публикуются.

## Технический формат существующих записей

Существующий [шаблон PR](../.github/pull_request_template.md) содержит краткое
соответствие ID → результат → проверка → статус и проверенную версию. Это формат
проверяемой записи, не новая ручная приёмка и не копия всего плана. Один сценарий
может подтверждать несколько пунктов; таблица без фактической проверки не доказательство.

node scripts/check-workflow-docs.mjs проверяет ссылки, бюджет и целостность
исторического архива; --pr-body проверяет существующий формат PR. Это не проверка
качества UI. Технический выбор применимых тестов — ENGINEERING_RULES; повторять
полный набор без изменившейся причины не нужно. Источники изменившихся требований
и ограничения проверки указываются в плане/PR, не в дополнительном журнале.
