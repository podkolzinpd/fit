# Fit — единый процесс работы

Для всех экранов, ролей, сервисов и служебных задач. Пользователь ставит задачу
и согласует план; исполнитель доводит разрешённый объём до проверенного результата.
Ручная приёмка каждого PR не добавляется. Общие правила не меняют rollout.

## Источники правды

1. Последнее подтверждённое решение пользователя и границы разрешения.
2. Канонический план и требования из [ACTIVE_CONTRACTS](ACTIVE_CONTRACTS.md),
   включая принятые SVG/handoff.
3. Реальный main, сборка и тесты — свидетельства текущей реализации.
4. [PRODUCT_WIKI](PRODUCT_WIKI.md) — реализованный продукт; Tracker — статус.
5. История — причины и доказательства, не автоматическая отмена нового решения.

«Есть в коде» не означает «согласовано». Принятый SVG действует без доступного
Figma-frame. Непринятый референс сам не меняет продукт. Существенный неясный конфликт
зафиксировать; обычные технические решения внутри scope не требуют согласования.

## Проверка существующего перед каждой доработкой

Проверить checkout/main/PR и релевантные параллельные изменения. По индексу найти
требования и прошлые ошибки области; прочитать причины и ограничения.
Для UI воспроизвести исходный сценарий на фактической роли/маршруте/флаге;
для backend/документов — соответствующий контракт. Указать проверенную версию.
Сопоставить с компонентами, токенами и покрытием; работающую функцию не создавать
повторно. Кратко сообщить «уже есть / переиспользуем / меняем / не проверено».
Перед следующим PR обновить сведения; после интеграции повторить затронутые
проверки. Недоступное не выдавать за проверенное; независимую работу продолжать.

## Контракт утверждённого плана

Один канонический план: существующий файл задачи либо тикет. Для multi-PR удобен
docs/design. Тикет и PR ссылаются на него, не требуют трёх полных копий.
Каждый пункт сохраняет ID, смысл, результат и ограничения. Нельзя молча вычеркнуть
или упростить пункт. Новое решение фиксируется как замена с причиной и историей.

В существующем PR — компактная таблица только его пунктов:

| ID | Результат | Проверка | Статус |
| --- | --- | --- | --- |
| P1 | Ожидаемое поведение | Сценарий/тест/просмотр и версия | проверено |

Один сценарий может закрыть несколько ID. Скриншот подтверждает вид, действие —
поведение. Документам нужны смысловая сверка, ссылки и целостность, не UI-тест.
Для небольшой правки достаточно одной строки. Статусы: «проверено»,
«не проверено», «согласован перенос» (со ссылкой на решение владельца).
Непроверенный пункт текущего PR мешает merge; следующие PR остаются в общем
плане и не требуют повторного разрешения.

Версию указать один раз: commit либо источник и hash затронутых файлов, если
проверка проведена до финального docs-коммита. CI должен относиться к final head.
Последующие связанные изменения требуют повторной проверки затронутого сценария.
Таблица сама по себе не является доказательством.

## Цикл одной задачи

1. Preflight и план; создать/обновить YAFIT без лишнего вопроса.
2. Минимально реализовать принятый результат, сохранив соседние механики.
3. Целевые проверки по [ENGINEERING_RULES](ENGINEERING_RULES.md); не добавлять
   дубли без новой регрессии и не принимать тест, который просто повторяет код.
4. UI проверять по [UI_TASK_PROMPT](UI_TASK_PROMPT.md): состояние до, действие,
   результат, применимые вложенные состояния и отсутствие несогласованного лишнего.
5. Проверить все ID, diff и git diff --check. Обновить нужный источник:
   реализованное — PRODUCT_WIKI, решение — контракт, статус — тикет.
6. PR с результатом и таблицей; дождаться очереди и зелёного CI. Падения разбирать,
   не ослаблять проверки и не перезапускать вслепую.
7. Слить и проверить результат. Для runtime — штатный выпуск точного main и
   ключевые сценарии по разрешённому rollout. Для docs — наличие правил в main.
8. Выполнить все следующие PR согласованного плана. Закрыть YAFIT после всего
   разрешённого объёма. Соседние проблемы записать, не включать молча в scope.

Если затронута mobile-сборка: после merge синхронизировать новый main, собрать,
установить и запустить свежий bundle. Старый симулятор не доказывает выпуск.
Не открывать второе окно Xcode. Docs без runtime не требуют native-пересборки.
Физическое устройство, симулятор и браузер — разные проверки.

## Проверки и скорость

Использовать scripts/e2e-scope.mjs для полного diff, включая working tree.
Non-frontend пропуск — только по его контракту; CI/shared/unknown требуют полного
набора. Полный npm run check после стабилизации diff; повторять по новому сигналу.
Для UI WebKit390, адаптация430, поддерживаемые темы; 360/375, desktop1440 и
другие устройства — по затронутой области/риску. Shared проверять у потребителей.
Не умножать поведенческий тест на все темы/размеры без причины.

Зависимости, Podman-базы и браузеры проверить до дорогих тестов; при одинаковом
lock переиспользовать рабочие зависимости. Новые данные проверять на локальном
API/PG, не только frozen Supabase fixtures. Production не тестовая БД.

## История, контекст и повторные ошибки

- AGENTS + workflow + CURRENT_STATE — компактный обязательный старт.
- CURRENT_STATE: максимум 12 KiB,120 строк,600 байт на строку. Только текущий индекс,
  проверенная точка, ограничения и ссылки, не журнал запусков CI.
- [ACTIVE_CONTRACTS](ACTIVE_CONTRACTS.md): действующие решения и причины по областям.
- [REGRESSION_LESSONS](REGRESSION_LESSONS.md): повторный дефект, причина, требуемая
  защита и фактический статус. «Нужна проверка» не означает «исправлено».
- Завершённая хроника сохраняется в Git/Tracker и [архивном индексе](archive/workflow-20261027/INDEX.md).
  Возраст документа не отменяет требования. Перед изменением области прочитать
  связанные решения/ошибки, а не всю историю продукта.
- Перед архивацией извлечь действующие ограничения, сохранить исходник и ссылки.
  Неясное пометить для проверки по области; не удалять и не объявлять закрытым.
- При неисправной корпоративной KB использовать поиск по этому репозиторию,
  а не зависеть от чужой базы. Не менять общие базы ради Fit.
- node scripts/check-workflow-docs.mjs проверяет бюджет, ссылки, архивы и структуру
  приёмки. Это защита от пропусков, не доказательство качества картинки.

## Коммуникация

Короткий статус примерно раз в минуту или после значимого шага. В итоге:
результат, проверки, PR/main, выпуск и ограничения. Не спрашивать повторно уже
данное разрешение. Внешний блокер назвать конкретно; частичное не выдавать за полное.
