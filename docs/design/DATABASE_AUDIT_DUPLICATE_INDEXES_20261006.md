# Удаление дублирующих индексов позиций тренировок

Два обычных индекса позиций повторяют ключи индексов UNIQUE-ограничений.
Новая Yandex migration125 удаляет только эти дубли. Данные, ограничения,
отложенная проверка уникальности, RLS и публичные контракты сохраняются.
Историческая migration008 и замороженная Supabase-цепочка не изменяются.

## Подтверждённая задача

> В миграциях есть два дублирующих индекса на позиции упражнений и подходов.
> Такие же ключи уже покрываются индексами UNIQUE-ограничений, которые
> PostgreSQL создаёт автоматически. Это дополнительное обслуживание индексов
> при записи. Перед удалением нужно сверить реальный каталог и планы запросов;
> ограничения сохранить.

Поток data-media, исходный main `e17ed22c`. Новая задача не продолжает
диагностику frontend-таймаутов и не меняет расчёты статистики.

## Индексы и запросы

Удаляются `public.workout_exercises_workout_position_idx` и
`public.workout_sets_exercise_position_idx`. Остаются
`workout_exercises_position_unique` на `(workout_id, position)` и
`workout_sets_position_unique` на `(workout_exercise_id, position)`.
После migration011/014 оба ограничения — DEFERRABLE INITIALLY IMMEDIATE;
этот режим необходим для перестановки позиций и не изменяется.

Training-data читает дочерние строки через `parent_id = ANY(uuid[])` с
сортировкой по parent, position, id. Индексы не включали id, поэтому удаление
дублей не убирает прежнее покрытие третьего ключа сортировки. В коде и
миграциях нет использования удаляемых имён, кроме их создания в migration008.

## Безопасность миграции

Миграция проверяет каталог той БД, к которой её применяют: таблицы, B-tree,
ключи и включённые колонки, операторные классы, collation, направление,
отсутствие predicates/expressions, валидность и готовность обоих индексов,
связь оставшегося индекса с действующим отложенным UNIQUE. У удаляемых
индексов не должно быть constraint или replica identity. При расхождении
миграция завершается ошибкой, не удаляя индекс.

Обе таблицы блокируются на время проверки и удаления в одной транзакции.
`lock_timeout=3s` и `statement_timeout=15s` ограничивают ожидание; при занятой
таблице миграция откатывается. Обычный DROP INDEX требует ACCESS EXCLUSIVE:
короткое ожидание других запросов возможно, нулевая блокировка не обещается.
CASCADE не используется. Down восстанавливает только два обычных индекса.

Это соответствует механизму [UNIQUE PostgreSQL17](https://www.postgresql.org/docs/17/indexes-unique.html)
и ограничениям [DROP INDEX](https://www.postgresql.org/docs/17/sql-dropindex.html).
CONCURRENTLY не используется, поскольку штатный runner применяет SQL в
транзакции. Ручной SQL или отдельный production apply не выполняется.

## Приёмка

1. Каталог: дубли подтверждены на локальной PostgreSQL17; миграция повторяет
   проверку при применении. Изменённый второй индекс блокирует удаление обоих.
2. Планы: читаемые строки и доступность ordered index path через UNIQUE
   сохраняются после down/up. На1000 синтетических тренировок,10000 упражнений
   и50000 подходов обычный EXPLAIN ANALYZE без planner overrides переключился
   с дублей на UNIQUE:10/50 строк, estimated total cost38.61/209.67 до и после.
   Данные эксперимента откатились. Один прогон не доказывает ускорение production.
   Маленький integration test дополнительно проверяет наличие index path.
3. Ограничения: немедленный дубль позиции отклоняется, перестановка при
   deferred проверке работает для упражнений и подходов. Занятый reader
   останавливает миграцию по lock timeout без удаления индексов.
4. Проверки: целевые тесты, clean Yandex chain/actor-RLS и полный check
   выполняются до передачи PR; результаты фиксируются ниже.

## Проверки и границы

Финальная чистая Yandex chain125 и полный actor/RLS:91/91, включая шесть новых
проверок. Финальный targeted6/6; WebKit3/3 (Today diagnostics и Lime
loading/error/retry/empty в обеих темах). Полный `npm run check` прошёл:
lint/typecheck, frontend2409/2409, API1159/1159 и build. В общем unit-run91 DB
тест skipped, отдельно выполнены91/91. `git diff --check` зелёный; CI — гейт PR.
Первый полный check нашёл unsafe pg query argument в новом тесте; явный generic
исправил типизацию, повторный полный check прошёл без ослабления правил.
`npm run local:verify` остановился на прежнем LegacyMigrationMissingRemoteError
для Supabase `20260919145000_source_cutover_migration_window.sql`. Baseline
не сбрасывается; новая Yandex-цепочка проверяется отдельно на чистой БД.

Первый clean-run остановил защитный guard из-за другого имени локальной БД;
guard не ослаблялся. Финальный запуск использует отдельный Podman PostgreSQL17
с разрешённым именем `fit_actor_test`. Производственные данные не затрагиваются.

Production-каталог, данные и секреты не читаются локальными тестами. Изменение
передаётся отдельным PR; миграция применится штатным rollout после merge.
UI, mobile bundle и продуктовые сценарии не меняются; новые UI states и
изменения PRODUCT_WIKI не требуются.
