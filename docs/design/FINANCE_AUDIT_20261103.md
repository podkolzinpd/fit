## Семь дополнительных находок

### AUD-11 / P1 — уменьшение пакета одновременно со списанием нарушает лимит

`update_trainer_finance_service` сначала читает число использованных занятий,
проверяет новый лимит, затем обновляет пакет. Общую блокировку клиентского
учёта, используемую завершением тренировки, эта функция не берёт.

На настоящем PostgreSQL выполнены две конкурентные команды одного тестового
тренера. Блокировка строки использовалась только как барьер, чтобы поставить
проведение второго занятия между проверкой остатка и обновлением лимита.

- Был пакет на2 занятия, одно уже списано.
- Редактирование проверило допустимость уменьшения до1.
- Параллельное проведение списало второе занятие.
- Редактирование успешно сохранило лимит1; в таблице остались2 списания.
- API вернул `sessionsUsed=1`, потому что ограничивает значение через `least`.

Ошибка воспроизведена и при нулевой стоимости, и на полностью оплаченном пакете
10 000 ₽. Цена и оплачено независимо перечитаны из локальной базы.
Последовательное такое же уменьшение после двух списаний правильно отклоняется
с PT422. Нарушение возникает именно из-за конкурентной проверки.

Основа: [чтение и проверка до обновления](https://github.com/podkolzinpd/fit/blob/3aec76296f896da9a30a6cc6a425a74cd297eaad/services/api/db/migrations/000109_trainer_finance_online_coaching.sql#L170),
[маскирующее ограничение счётчика](https://github.com/podkolzinpd/fit/blob/3aec76296f896da9a30a6cc6a425a74cd297eaad/services/api/db/migrations/000109_trainer_finance_online_coaching.sql#L55).
Исправление должно сериализовать изменение пакета и списание, проверяя лимит
после блокировки. Массовый пересчёт исторических записей в этот аудит не входит.

### AUD-06 / P2 — финансовый обзор остаётся прежним после оплаты

После создания/редактирования услуг, оплаты, удаления оплаты и изменения учёта
страница обновляет только `['trainer-finance', clientId]`.
`['trainer-finance-overview', month]` не инвалидируется. В приложении кэш
считается свежим20 секунд; истечение срока само по себе не гарантирует новый запрос.

Реальные React-компоненты с production `staleTime` воспроизвели: долг15 000 ₽,
оплата5 000 ₽, карточка уже перечитана, возврат в обзор всё ещё показывает15 000 ₽
вместо10 000 ₽. Исходный QueryClient существующих component-тестов не задаёт
production `staleTime`, поэтому проверка только карточки этот дефект не ловит.

Основа: [локальное обновление](https://github.com/podkolzinpd/fit/blob/3aec76296f896da9a30a6cc6a425a74cd297eaad/src/features/finance/TrainerFinancePage.tsx#L236),
[политика кэша](https://github.com/podkolzinpd/fit/blob/3aec76296f896da9a30a6cc6a425a74cd297eaad/src/app/query-provider.tsx#L9).
Нужно согласованно обновлять связанные финансовые представления, включая месяцы,
которые затрагивает исправление даты платежа. Общая очистка всех данных не нужна.

### AUD-10 / P1 — финансовая история бывшего клиента недоступна через интерфейс

После отключения тренера сервер правильно запрещает доступ к текущей карточке,
но сохраняет разрешение читать собственные финансовые записи. В PG одновременно
получены `can_access_client=false` и финансовый пакет прежнего тренера.

Страница требует успешной загрузки и карточки клиента, и финансов. Ошибка
`clients.get` скрывает весь финансовый экран, хотя разрешённый bundle получен.
Независимый UI-сценарий воспроизвёл это состояние. Repository `clients.get`
действительно ищет карточку только в доступных активных/архивных списках.

Основа: [объединение ошибок](https://github.com/podkolzinpd/fit/blob/3aec76296f896da9a30a6cc6a425a74cd297eaad/src/features/finance/TrainerFinancePage.tsx#L354),

доступ к закрытой текущей карточке и приватным данным ради финансов нельзя.

### AUD-12 / P2 — изменение периода не проверяет существующие списания

Сервер разрешил закончить пакет2ноября, сохранив в нём списанное занятие3ноября.
Ни отказа, ни перевода на ручной выбор пакета не произошло. При изменении даты
самого занятия такая проверка есть; изменение условий услуги её обходит.

нужны явное правило и проверка затронутых списаний. Автоматически переставлять
исторические занятия между пакетами нельзя.

## Отдельное решение: долг за занятие без услуги

Сейчас денежный долг равен стоимости услуги минус её действующие оплаты.
У отдельной тренировки поля цены нет. Завершение не создаёт ни оплату, ни
денежное начисление — это соответствует исходной модели
([раздел1](trainer-finance-cabinet-20260930.md#1-основные-правила)).

Поэтому нельзя обоснованно прибавить к «К оплате» произвольную стоимость за
занятие без абонемента. Минимальное существующее действие — поставить занятие
на контроль, затем связать с услугой с указанной ценой. Разовое занятие уже
может быть услугой из одного занятия. Если нужен автоматический денежный долг,
надо отдельно определить источник цены и момент начисления. AUD-01 необходимо
исправлять независимо от этого решения.

## Что не следует считать найденной ошибкой

- На скриншотах20 000 ₽ в карточке за всё время и10 000 ₽ за ноябрь не
  противоречат друг другу: одна оплата датирована31октября, другая3ноября.
- Финансовая история архивных клиентов должна сохраняться. Её неудобное
  отображение не разрешает удалять записи или исключать старые поступления.
- Две одинаковые подписи имени не доказывают дубль клиента. SQL группирует
  обзор по ID и объединяет scope через UNION; конкретные карточки не сливались.
- Сохраняются денежные суммы в копейках, фактическая дата получения, расчёт из
  неотменённых платежей, задолженность истёкших/израсходованных незакрытых услуг,
  actor-scoped доступ и защита повторной отправки. Это проверено целевыми тестами;
  банковские операции и реальный учёт пользователей аудит не сверял.

## Итерация1 — 2026-11-03 — Codex / OpenAI

Задача: аудит финансов по пяти скриншотам и независимая проверка кода/алгоритмов.
Расхождения: AUD-01 противоречит принятому правилу непривязанных занятий;
AUD-11 нарушает явный серверный запрет уменьшать пакет ниже использованного.
Ни наличие кода, ни старое положительное ожидание теста не отменяют требования.
Сделано: подняты прежние финансовые планы, сверены актуальные определения

приватности не расширять, причины UX отделить от потери учёта и отсутствующих видов.
Отвергнуто: массовый пересчёт старых данных, случайный выбор пакета, удаление
архива, отключение SQL replay/conflict guards, попутные исправления и выпуск.
