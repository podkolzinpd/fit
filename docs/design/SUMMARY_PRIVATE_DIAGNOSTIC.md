# Закрытая диагностика отказа ИИ-анализа

## Подтверждённый план

1. Проверить её актуальный код и конкретные правила, перечисленные в журнале.
2. Добавить ограниченную диагностику только для тестового клиента: возвращать отклонённый ответ и причины через авторизованный запрос, без публикации в логах и без сохранения анализа.
3. Выполнить один запрос и сопоставить каждую претензию проверки с конкретной фразой.
4. Исправить доказанную причину и убрать временную диагностику.

## План исправления после реального ответа

1. Исправить ложное совпадение: «стабильность результатов упражнения» не
   является замечанием о коротком перерыве между тренировками.
2. Разделить проверки на блокирующие фактические ошибки и стилистические
   замечания. Фактические ошибки по-прежнему отклоняют ответ; стилистика
   получает одну попытку переписывания, после чего безопасный ответ сохраняется.
3. Запретить неподтверждённые выводы об улучшении техники и причинные заявления,
   которых нельзя получить из дневника. Усилить prompt до цепочки
   «конкретное движение/замер → проверяемое изменение → интерпретация → действие».
4. Выпустить исправление обычным PR, проверить обновление на production и только
   после успешного сохранения удалить временную диагностику отдельным PR.

## Контракт и границы

Используется существующая функция, её сборщик и Supabase authentication/ownership.
Новые IAM-аккаунты, секреты и изменения БД не нужны. Только подтверждённый
тестовый email (проверяется по хешу на сервере), только собственная карточка.
Временное разрешение истекает 13 сентября 2026 в 00:00 UTC.
Обычный запрос без diagnostic сохраняет прежнее поведение.

POST с обычными client_id/period_start/period_end и diagnostic=preflight
не вызывает модель и не пишет в БД. Возвращает счётчики и fingerprint.
POST diagnostic=run_once требует diagnostic_fingerprint из preflight;
изменившийся вход отклоняется до вызова модели. Один запрос к модели без
повторов, только direct-вход до 80 000 символов. Возвращает исходный ответ,
статус завершения, причины проверки и usage через no-store HTTP response.
Ни положительный, ни отрицательный ответ не сохраняются как анализ.
Название run_once ограничивает вызовы внутри одного запроса, а не создаёт
durable глобальный лимит: оператор выполняет его один раз, при неоднозначном
сетевом результате не повторяет. Ответ не публикуется в Git/логах/аналитике.

## Фактура до диагностического вызова

- production отвергает ответы quality gate; ошибка инфраструктуры не доказана;
- правило коротких перерывов ищет также подстроку «стабильност» без контекста;
- правило клиентского императива запрещает «проверить» независимо от контекста;
- эти дефекты правил не доказывают конкретный текст production-ответа.

## Приёмка

Временный вход: `/me/progress?summaryDiagnostic=1`. Обычный Progress не меняется.
Переиспользованы `ai-progress-card`, `client-progress-card`, primary button и
обычная ссылка возврата; новых цветов/токенов/навигации нет. Один primary на шаг:
сверить вход → один вызов. Несовпадение 14/149/376/44511 блокирует вызов.
Ответ выводится как экранированный текст без HTML. Pending блокирует двойной
тап; после начала платного запроса повтор блокируется в состоянии и sessionStorage.
Это служебный Supabase-only путь; Yandex session не получает обхода авторизации.
