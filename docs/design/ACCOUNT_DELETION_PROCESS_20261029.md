## План

1. P1: разрешить ровно одну учётку по приватному хешу адреса, сверив legacy
   registry и сохранённые Cloud.ru bindings. Неоднозначность останавливает
   процесс. Получить read-only счётчики зависимостей без персональных данных.
2. P2: по фактическим связям подготовить ограниченное удаление личных данных,
   сессий и login bindings; сохранить чужие аккаунты и их независимые данные.
   Раздельные системы проверять отдельно; не заявлять атомарность между ними.
3. P3: выполнить после проверок, перечитать источники и подтвердить отсутствие
   учётки/доступа. Оставить только обезличенный операционный результат.

P2 подготавливается отдельно от неизменного кода P1. Контур строго ограничен
клиентом с одной native Yandex identity и принадлежащими ему client cards.
Точное обращение проверяется повторно в транзакции. Смешанные/слитые карточки,
финансы, custom exercises, чужое авторство вне этих карточек, chat media,
активные встречи и отправляемые push требуют отдельного разбора: до записи
процесс останавливается. Произвольный recursive purge не используется.

Удаление profile/cards/workouts и принадлежащих агрегатов выполняется одной
serializable-транзакцией с блокировками корней, ограничением числа строк и
проверкой ожидаемого удаления. Сессии, legal/feedback/preferences/assistant/
nutrition очищаются существующими FK; feature bindings и auth handoff —
явно. Чужие push удаляются только при точной структурной ссылке на удаляемую
сущность. Независимые legacy-источники не изменяются.

Перед COMMIT сохраняется закрытая квитанция без контактов/контента, только
opaque IDs и fingerprint разрешённого scope. Она находится на сервере в
root-only директории 0700, файл0600; запись синхронизируется с диском до COMMIT.
При потере ответа COMMIT нельзя повторять apply: сначала verify по номеру
операционного run. Успешный readback удаляет квитанцию. Ошибка оставляет её
для проверки. Public summary содержит только статус/счётчики, без IDs/хешей.

Применение P2 разрешено только с проверенного текущего main после успешного
main CI. Исключение владельца для read-only P1 не распространяется на write.
Реальное удаление и проверка зависимостей на production ещё не выполнялись.
