# Новый Progress: измеримые критерии цели

Статус: утверждённый продуктовый контракт. Исходная нумерация и формулировки
сохранены без сокращений.

Начинай реализацию нового Progress строго по приложенному плану.

Главное правило: не делать это одним большим изменением. Работай последовательно:

**1.1 → 1.2 → 1.3**

Каждый выпуск должен быть полностью закончен, протестирован и оформлен отдельным PR до перехода к следующему.

### Общие ограничения

1. План является продуктовым контрактом. Не упрощай и не меняй заложенную в нём логику без объективной технической причины.
2. Сначала изучи существующую реализацию:

   * Progress;
   * goals / goal stages;
   * measurements;
   * workout results;
   * LLM-интеграцию;
   * БД и текущие типы/API;
   * существующие тесты.
3. Сохрани полную обратную совместимость с уже созданными целями и историческими данными.
4. Никаких destructive migrations и потери пользовательских данных.
5. LLM только:

   * интерпретирует текст цели;
   * предлагает критерии;
   * выявляет неоднозначности;
   * формулирует объяснение уже рассчитанных фактов.

   LLM **не имеет права** рассчитывать статус цели, числовой прогресс, проценты, направление движения или самостоятельно менять критерии.
6. Все расчёты должны быть deterministic и выполняться обычным кодом с unit-тестами.
7. Если LLM недоступна, ручная настройка и расчёт Progress должны продолжать работать.
8. Не менять глобальные настройки модели/provider/temperature и общую архитектуру LLM без необходимости.
9. UI делать в уже утверждённой monochrome design system:

   * существующие токены;
   * существующие компоненты;
   * установленная типографика;
   * light/dark;
   * mobile-first;
   * никаких новых локальных цветов и самостоятельной визуальной системы.
10. Не менять постороннюю продуктовую логику и не рефакторить код вне необходимого scope.

### 1.1 — Основа цели

Реализовать только после анализа текущей архитектуры:

* структуру критериев оценки;
* связь критерия с целью;
* подтверждение пользователем;
* направления/operations;
* target / range / unit;
* состояния:

  * настроено;
  * не настроено;
  * нужны данные;
* возможность сохранить цель вообще без автоматической оценки;
* ручную настройку критерия без LLM;
* новый базовый контракт карточки Progress;
* безопасную миграцию существующих целей.

Если старая цель не имеет критерия, она должна продолжить существовать и отображаться как цель без настроенной автоматической оценки.

Не пытайся угадывать критерий для старых целей автоматически.

Покрой доменную модель и расчётные состояния unit-тестами.

После реализации:

* typecheck;
* unit;
* integration;
* Chromium;
* WebKit;
* visual regression;
* проверка light/dark;
* проверка mobile.

Создай отдельный PR для 1.1.

Только после успешного завершения 1.1 переходи к 1.2.

### 1.2 — Вес и стандартные измерения

Добавить:

* weight;
* waist;
* chest;
* hips;
* decrease_to;
* increase_to;
* maintain_range;
* change_by;
* track_only;
* исходное значение для относительных целей;
* текущее положение;
* отдельную динамику;
* достаточность данных;
* freshness/staleness;
* корректную работу выбранного отчётного периода;
* различие между «значением на конец периода» и самым свежим значением сейчас.

Для удержания не объявлять цель удерживаемой по одному измерению.

Не использовать скрытые magic numbers. Если существующих продуктовых правил для количества измерений, периода удержания или freshness нет — вынеси их в централизованные именованные policy/constants, покрой тестами и зафиксируй принятое правило в документации PR.

Реализовать все проверочные сценарии из плана для стандартных измерений.

Отдельный PR для 1.2.

Только после полной проверки переходить к 1.3.

### 1.3 — Тренировки и составные цели

Добавлять по очереди:

1. exercise criteria;
2. working weight / reps / volume / best result;
3. cardio distance / duration / pace / distance+time;
4. regularity;
5. custom metrics;
6. несколько критериев в одной цели.

Для упражнений использовать только реально существующие упражнения. Неоднозначное совпадение требует подтверждения пользователя.

Для связанных cardio-условий данные должны относиться к одной тренировке.

Для регулярности различать среднее количество тренировок и выполнение требования в каждом периоде.

Для custom metric название показателя само по себе не определяет направление улучшения.

Каждый criterion рассчитывается независимо.

Для составной цели не сворачивать результат в ложный бинарный статус. Показывать фактический результат каждого критерия и количество выполненных критериев.

### Создание/изменение цели через LLM

LLM должна возвращать строго структурированный ответ, который:

1. валидируется схемой;
2. проверяется обычным кодом;
3. показывается пользователю;
4. активируется только после подтверждения.

Никакой автоматической активации предложенного LLM критерия.

При изменении текста существующей цели не переиспользовать старый критерий молча — пользователь должен проверить новую интерпретацию.

### Progress card

Карточка должна работать независимо от LLM и показывать deterministic facts:

* название цели;
* criterion;
* status;
* current value;
* target/range;
* period dynamics;
* last measurement/result date;
* data sufficiency;
* freshness;
* CTA при отсутствии данных или настройки.

Статус нельзя обозначать только цветом.

LLM explanation — дополнительный слой поверх рассчитанных фактов, а не источник истины.

### Edge cases

Обязательно пройти весь список пограничных и проверочных сценариев из исходного плана.

Особенно:

* несколько чисел;
* отсутствие unit;
* decimal comma;
* диапазоны;
* ambiguous exercise;
* удалённая metric;
* 0/1 measurement;
* historical corrections;
* данные после выбранного периода;
* unsupported LLM output;
* LLM unavailable;
* medical wording;
* unrealistic values;
* составные цели с частичным выполнением.

### Порядок работы

Работай автономно и не перескакивай через этапы.

Для каждого выпуска:

**анализ → реализация → миграции → тесты → browser/visual QA → документация → PR → проверка результата → следующий выпуск.**

Не объединяй 1.1, 1.2 и 1.3 в один PR.

## Статус реализации

- 1.1 — выполнено отдельным выпуском: foundation критериев и ручная настройка.
- Исправление self-service — выполнено отдельным выпуском для standalone и
  linked клиента с сохранением доступа тренера.
- 1.2 — выполнено отдельным выпуском: фактический расчёт стандартных замеров.
- 1.3 — выполнено отдельным выпуском: exercise/cardio/regularity/custom,
  составные цели и LLM-предложения с явным подтверждением. Источником
  progress/status/direction остаётся только deterministic-код.

Если обнаружишь техническую проблему, сначала ищи решение, сохраняющее продуктовый контракт. Не сокращай функциональность просто ради более простой реализации.

Начинай сейчас с анализа текущего кода и реализации **1.1**.
