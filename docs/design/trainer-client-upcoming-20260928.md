# Тренировки клиента: видимость текущих и будущих планов

Поток: product. База: `883d5ffb`. Отдельная задача без изменений auth,
сохранения, БД, backend routing, главных экранов и дизайна календаря истории.

## План и acceptance

1. Добавить «Предстоит» с планами на сегодня и будущее, независимо от страниц истории.
2. Сохранить прошлые планы и завершённые тренировки в своих разделах. «Предстоит» будет видно и при включённом календаре истории.
3. Проверить пустой список, загрузку, ошибку с повтором, переход в тренировку и возврат, начало и завершение.
4. Пройти мобильные проверки и CI, затем выпустить и проверить опубликованную сборку.

## Причина и контракт

`ClientWorkoutsPage` загружал только даты по сегодня, но выводил лишь
`splitClientWorkouts().needsDecision/history`. Текущие planned/in_progress
попадали в upcoming и не отображались, будущие даты вовсе не запрашивались.
Конкретная production-запись пользователя не проверялась; диагноз подтверждён
по коду и воспроизведён тестом маршрута: до исправления текущие и будущие
карточки отсутствуют при наличии записей в ответе repository.

Историческая причина проверена по Git: PR #22 (`9130ed16`, 23 июля) вынес
upcoming на карточку клиента и сделал этот маршрут только историей. PR #390
(`293a3bb6`, 16 августа) ограничил запрос датой сегодня. PR #502 (`6dcc3e81`,
21 августа) переименовал экран в «Тренировки клиента» и добавил прошлые планы,
но не upcoming. Это незавершённое расширение старого history-only контракта,
а не доказанная регрессия переезда в Yandex.

Визуальная проверка длинных названий выявила растяжение вложенных grid-треков.
Они ограничены `minmax(0, 1fr)`, а тест проверяет координаты карточек, не только
ширину документа (overflow-контейнер скрывал проблему от прежней проверки).

Референс: `/me/workouts`, существующая секция «Предстоит». Переиспользуются
`Page`, `AsyncView`, `EmptyState`, `WorkoutExercisesSummary`, `WorkoutStatusBadge`,
`client-workout-card/section` и действующие семантические токены. Единственный
primary — «Запланировать». Карточка ведёт в существующий detail с `returnTo`.

Repository-контракт — `list(today, undefined, clientId)` для upcoming,
`listPage(undefined, today, ...)` для истории. Оба уже поддерживаются Supabase
и Yandex; provider-specific поведение не добавляется. Новый флаг не нужен:
это исправление исчезающих записей, а не новый путь создания данных.

Календарь остаётся календарём **истории**, текущие/будущие планы доступны над
ним в «Предстоит». Прошлый planned остаётся в «Ранее запланировано», done и
cancelled — в истории. При ошибке/загрузке не показывать ложное пустое состояние.

## Доказательства

1. «Предстоит»: воспроизведение до исправления (0 вместо 3 карточек), затем
   WebKit для Trainer и Client — сегодня planned/in_progress и будущий planned
   видимы, порядок дат сохранён, длинные названия не выходят за 390/430/1440 px.
2. Прошлые планы/история/календарь: тот же тест проверяет отдельные секции,
   сохранение upcoming в режиме календаря и возврат из detail. Регрессия всего
   `client-workout-calendar.webkit.spec.ts`: 20 passed + 1 flaky (старый тест
   входа прошёл на повторе; локальный Auth ранее возвращал JWT issued at future).
3. Live → completion → история и loading/error/retry/empty: отдельные WebKit
   сценарии прошли. Provider/repository unit: 143 passed.
4. `npm run check` прошёл: frontend 2057, API 943 (49 DB-dependent skipped),
   lint/typecheck/build и служебные проверки. Yandex mocked API проверен с
   Fit Lime on/off, light/dark, 390/430/1440 (2 сценария). Скриншоты реального
   маршрута просмотрены. CI/merge/production — следующие обязательные гейты;
   до их подтверждения выпуск не считается завершённым.

Локальный дополнительный `local:verify`: Supabase pgTAP 1485 checks passed;
долгоживущая локальная Yandex test DB остановилась на старом порядке двух
миграций `000059`. Схема/миграции этим PR не меняются; clean-chain CI остаётся
обязательным. Production-запись budoha1 и вход под реальным аккаунтом не
проверялись: пользовательские данные не изменялись.
