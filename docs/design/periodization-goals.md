# Периодизация (упрощённая): Цель + Подцели-этапы

Статус: **спека согласована, реализуется в 2 захода.** Из XL-периодизации взят
минимум — то, что реально нужно сейчас.

## UX: прогрессивное раскрытие (важно)
Цель эволюционирует, не путая тех, кому нужна одна строка:
- **Нет цели** → `[＋ Поставить цель]`.
- **Цель = текст + дата** (минимум, многим хватит) → показываем цель + «осталось
  N дней» + ненавязчивую подсказку-карточку «Хотите разбить путь на этапы?».
- **Цель + этапы** → подсказка исчезает, вместо неё прогресс «этап 2 из 3».
Один блок «Цель», без режимов/переключателей. Периодизация видна (подсказка с
примером), но не навязана.

## Заходы
- **Заход 1A (S, 0 миграций) — СДЕЛАНО:** блоки «Цель» и «Заметка» в карточке
  клиента с **редактированием прямо в карточке**, через существующий RPC
  `update_client` (уже умеет goal + note). Закрывает баг: раньше цель/заметку
  тренер не мог править из карточки (была только read-only + «Мои настройки» =
  приватный alias, не цель). Плюс подсказка-заглушка «Разбить путь на этапы»
  (dashed-карточка, кнопка «Скоро») — делает периодизацию заметной, не навязывая.
  **Цель и Заметка — два независимых блока** (каждый со своей кнопкой «Изменить»):
  заметка — это приватный комментарий тренера о клиенте (`client_private_details`,
  травмы/ограничения), не часть цели, поэтому вынесена отдельно и переживёт
  добавление даты/этапов к цели в Заходе 2. Обе формы сохраняют через один
  хелпер `useSaveClient`, всегда передавая текущее значение соседнего поля, —
  правка цели не затирает заметку (update_client пишет оба поля одной транзакцией).
- **Заход 2 M1 — СДЕЛАНО:** цель как сущность (`client_goals`: title + `target_date`
  + status, одна активная) + этапы (`goal_stages`: title + период) + RLS + RPC
  (`get_client_goal`, `save_client_goal`, `archive_client_goal`, `save_goal_stage`,
  `delete_goal_stage`) + pgTAP (0024, 14 тестов) + domain/queries/repository +
  логика `goal-rules.ts` (текущий этап по дате, «осталось N дней», «этап N из M»)
  + unit-тесты + экран цели `/clients/:id/goal` (CRUD этапов, архив). Блок «Цель» в
  карточке теперь показывает title сущности + дату + «осталось N дней» + текущий
  этап; кнопка-заглушка «Скоро» стала ссылкой «Оформить/Открыть →». Старый
  текстовый `clients.goal` — fallback (показывается + inline-правка), если сущности
  ещё нет, с предложением «оформить с датой/этапами».
- **Заход 2 M2 (следующий PR):** привязка тренировки к этапу (`workouts.stage_id`)
  + поле «Этап» в форме тренировки + метка этапа. Трогает горячий workout-путь
  (save_workout/list_workouts), поэтому отдельным PR.

## Что делаем / чего НЕ делаем
**Делаем:**
- **Цель** клиента (одна активная): название + дата достижения.
- **Этапы (подцели)** внутри цели: название + период (дата начала-конца).
- **Привязка тренировки к этапу** при планировании (необязательная).
- Текущий этап определяется по сегодняшней дате.

**НЕ делаем сейчас** (сознательно вырезано из XL):
- ❌ Женский цикл
- ❌ Разные модели периодизации (только линейная = последовательность этапов)
- ❌ План нагрузки на этап vs факт
- ❌ Автопланирование «от даты назад» (тренер задаёт этапы сам)

## Модель данных
Одна активная цель на клиента + этапы + мягкая ссылка у тренировки.

```
client_goals
  id, client_id, trainer_id, created_by
  title            text        -- «Похудеть к отпуску»
  target_date      date        -- дата достижения
  status           text        -- 'active' | 'archived'
  version, created_at, updated_at, archived_at
  (частичный уникальный индекс: один active на client_id)

goal_stages
  id, goal_id, trainer_id
  title            text        -- «Сушка»
  starts_on        date
  ends_on          date
  position         smallint    -- порядок
  version, created_at, updated_at

workouts
  + stage_id       uuid null   -- мягкая привязка тренировки к этапу (nullable)
```
RLS по владельцу (как остальные клиентские данные). Клиент видит свою цель/этапы
(read-only), пишет тренер.

## Экраны (макеты)

### 1. Карточка клиента — блок «Цель»
```
🎯 ЦЕЛЬ
Похудеть к отпуску
до 15 августа · осталось 18 дней
▓▓▓▓▓▓░░░░  этап 2 из 3 · «Сушка»
                              [Открыть →]
```
Нет цели → `[＋ Поставить цель]`.

### 2. Экран цели (новый)
```
← Похудеть к отпуску                 [Изменить]
До 15 августа · осталось 18 дней

ЭТАПЫ
 ✓ 1. Разгон метаболизма   1–14 июля · завершён
 ● 2. Сушка                15 июл–5 авг · идёт  ← сейчас
 ○ 3. Поддержка формы      6–15 авг
                       [＋ Добавить этап]

[Запланировать тренировку →]
```
Статус этапа (завершён/идёт/впереди) — по датам относительно сегодня.

### 3. Форма тренировки — выбор этапа
```
Клиент:  [Анна ▾]
Дата:    [27.07.2026]   Время: [10:00]
Этап:    [Сушка (2) ▾]  ← НОВОЕ, необязательно, по умолчанию — текущий по дате
Заметка / Упражнения ...
```
Если у клиента нет цели — поле «Этап» не показывается.

### 4. Метка этапа в тренировке
В карточке/деталях/истории тренировки — маленькая метка: `🎯 Сушка`.

## Логика
- **Текущий этап** = этап, где `starts_on ≤ сегодня ≤ ends_on`. Прогресс к цели =
  дни до `target_date`.
- При планировании тренировки поле «Этап» по умолчанию = текущий этап (можно
  сменить/убрать).
- Завершение/архив цели — вручную («Изменить» → архивировать); ставя новую,
  старую активную архивируем.

## Объём и дробление
**M** целиком, но можно резать:
- M1: цель (создать/показать в карточке/архив) + экран цели с этапами (CRUD этапов).
- M2: привязка тренировки к этапу (поле в форме + метка в тренировке).
Обе части ценны по отдельности; M1 уже даёт «ведём к цели со структурой этапов».

## Технически
- Миграции: `client_goals`, `goal_stages`, `workouts.stage_id` (nullable) + RLS +
  RPC (create/update/archive goal, CRUD stage, set workout stage). pgTAP.
- Domain-типы + repository + queries. schema-sha256.
- UI: блок в карточке клиента, экран цели, поле «Этап» в форме тренировки, метка.
- Тесты: pgTAP (один active на клиента, RLS клиент читает-не-пишет), unit
  (текущий этап по дате, прогресс), e2e (поставить цель → этап → привязать
  тренировку → метка видна).
