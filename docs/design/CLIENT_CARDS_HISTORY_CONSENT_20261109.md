# Карточки без регистрации и согласие на прошлую историю

Задача: [YAFIT-706](https://st.yandex-team.ru/YAFIT-706).

## Запрос владельца — 09.11.2026

1. мы отрезали тренеру возможность заводить клиентов без их регистрации - эту функцию нужно вернуть (не сломав больше ничего) - нужно дать возможность создавать карточки клиентов
2. при смене тренера новый тренер должен видеть все исторические тренировки клиента (но для этого нужно у клиента спрашивать согласие, предлагаю этот пункт либо в настройках отразить, либо где-то в меню связки, предложи)

Уточнение: «исторические тренировки включая тренировки с другими тренерами».

Предложение, принятое владельцем: спрашивать согласие прямо при подтверждении нового тренера: выключенный по умолчанию пункт «Открыть этому тренеру всю мою историю тренировок, включая занятия с другими тренерами». После подключения — управление и отзыв доступа в «Мой тренер». Без согласия подключение возможно, но прошлая история скрыта.
Ответ: «Да, при подключении + управление в „Мой тренер“».

## Уточнение владельца: три ползунка

«я бы вот тут сделал ползунки:

вся история тренировок
история самостоятельных тренировок
питание».

Принято: «Вся история тренировок» открывает и занятия с прежними тренерами, и самостоятельные; при выключенной «Всей истории» второй ползунок может открыть только самостоятельные. Питание — отдельное разрешение.
Ответ: «Да, вся история включает самостоятельные».

Подтверждён путь создания карточки: «Клиенты» → «Добавить спортсмена» → «Создать карточку без регистрации»; ответ владельца: «гуд».

## Реализация

- Forward migrations205/206, без backfill согласия или переноса тренировок.
- Прежние команды создания/подключения, обязательное взаимное подтверждение зарегистрированных аккаунтов и одна активная связь сохранены.
- `TrainerHistoryConsent` переиспользует Fit `Switch`; формы — прежние `Page`/`Field` и Lime/существующие токены. Главные страницы и навигация не перерабатываются.
- Native schema принадлежит `services/api/db/migrations`; замороженный Supabase generated types файл отсутствует в актуальном main и не восстанавливается.
- Для новой рабочей копии переиспользованы закреплённые зависимости. Podman VM не удерживается в running; проверки выполняются отдельным локальным PostgreSQL17 на55474 с синтетическими данными и отдельными БД.
- Production/Preview не запускались; после локальной проверки — PR и зелёный CI, без автоматического merge.

Уточнение владельца по скриншоту: «кнопку пригласить мы же договорились выпилить ранее, почему она опять есть?»; «так ссылки могут также создаваться в мой qr». Кнопка «Пригласить» удаляется с /connect; «Мой QR» сохраняет персональную ссылку и отправку. Проверяется продолжение после регистрации и взаимное подтверждение без создания пустой карточки. Прежние уже выданные приглашения поддерживаются.

Визуальная коррекция: исходные native аккаунты не имели Lime gate, поэтому ранние скриншоты показывали базовый монохром. Финальные проверки явно назначают только UI gates в synthetic profile response, подтверждают CSS scope и сохраняют реальную локальную авторизацию/данные/mutations. Production assignments не меняются.

Последняя коррекция владельца: «я бы в самый низ убрал, а то как будто основной сценарий». Вход создания карточки без регистрации находится внизу /connect как вторичный текстовый пункт; поиск и QR выше.

## Переход ручной карточки в аккаунт: уточнение владельца

Существующая привязка/каноническое объединение сохраняет тренировки, результаты, расписание и финансы, но блокирует совпадающие замеры, показатели, активные цели/тренировки и отчёты. Владелец отклонил блокировку и автоматический приоритет аккаунта: «нет, мы просто должны сказать, что есть расхождения и в каких данных, дальше дать выбор по конфликтующим, что брать за основу».

CH109: до подключения показать конкретные расхождения обеих карточек без выбранного по умолчанию источника. Неконфликтующие данные объединяются; для каждого расхождения требуется явный выбор клиента. Отмена/неполный выбор ничего не меняют. Изменение данных после просмотра требует новой проверки. Подтверждение атомарно с подключением; повтор не применяет решения заново. Исходные значения сохраняются для проверки результата, авторы/результаты тренировок и финансы не теряются.

Реализация207: сравнение полей карточки (включая различающиеся фотографии), замеров/InBody, значений показателей, единиц, целей с этапами/критериями, текущих тренировок с подходами и отчётов. Разные поля одного замера выбираются независимо; отсутствующие значения дополняются. Показатели с одинаковыми именем/единицей объединяются без потери строк значений; разные единицы не конвертируются молча. Для двух текущих целей клиент выбирает текущую, другая архивируется; для двух Live выбирает текущую, другая сохраняется для последующего возобновления с прежними фактами и временем. Обе версии отчётов остаются, writers обновляют только выбранную текущую. Закрытая квитанция хранит исходные значения и выбор, чужой formerly-bound источник нельзя даже сравнить по bearer-ссылке. Повторное применение после отката прежних модулей проверено.

Локальная итоговая проверка: полный `npm run check` — frontend3183/API1635, обе сборки; штатный DB/RLS-набор485 passed/2 прежних opt-in skipped; Chromium8 native сценариев, WebKit/desktop2 сценария сравнения. Обновлены только4 baseline клиентского профиля (две платформы/две ширины), где добавлены согласованные переключатели: Linux actual/diff из CI просмотрены, macOS сценарий2/2 прошёл, остальные снимки профиля/настроек прежние. Первый DB-прогон выявил неповторяемое применение207 — исправлено; повтор с общей проверкой дал5s timeout тяжёлого seed, отдельный полный DB-прогон без конкуренции зелёный, таймауты/assertions не менялись.
