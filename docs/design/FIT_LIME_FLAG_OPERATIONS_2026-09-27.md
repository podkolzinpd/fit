# Fit Lime: персональный флаг и безопасное отключение

Пункт 12 плана `FIT_LIME_ROLLOUT_PLAN_2026-09-27.md`. Этот выпуск добавляет назначение и контракт флага; общая оболочка и перерисовка экранов выполняются в следующих пунктах. Флаг расписания `trainerScheduleV2` остаётся независимым.

## Граница пилота

- Закрытый список ограничен тремя SHA-256-хэшами нормализованных значений поля `login`, которые возвращает Yandex ID для согласованных тренеров. Миграция `000127` поднимает предел до трёх, сохраняя два прежних назначения; третий подтверждённый ключ добавляется отдельным закрытым workflow, не миграционным исходником. У второго тренера Yandex ID возвращает нативный логин `mr.vidishev`, а не адрес `mr.vidishev@yandex.ru`; миграция `000098` исправляет первоначальный ошибочный хэш email одновременно для Schedule V2 и Fit Lime. Сырые логины и адреса в таблице не хранятся.
- Сервер связывает запись списка только с подтверждённой идентичностью Яндекса, существующим профилем тренера и карточкой тренера. Другой профиль не может занять уже связанную запись.
- `app_private.fit_lime_enabled()` возвращает `true` только для собственного авторизованного профиля тренера со связанной и включённой записью. API отдаёт значение как `profile.experiments.fitLime`.
- Клиентская проверка дополнительно требует роль `trainer` и `fitLime === true`. Отсутствующее поле и Supabase-ветка считаются выключенным флагом. `trainerScheduleV2` не служит запасным признаком Fit Lime.

## Отключение и проверка

Подключение третьего тренера: после штатной выкладки migration127 и API запускается main-only workflow `enroll-fit-lime-trainer.yml` с подтверждением `ADD_ONE_REVIEWED_TRAINER`. Ключ берётся только из repository secret `FIT_LIME_ADDITIONAL_TRAINER_LOGIN_SHA256` и отправляется IAM-защищённому migration runner (`POST /stage/experiments/trainer-lime-cohort`), а не обычному API. Owner-only SQL-функция атомарно добавляет запись в оба списка и отклоняет четвёртую. Workflow проверяет `approvedRows=3`, затем повторяет операцию и требует `added=false`; отчёт содержит только эти два поля. Ключ не попадает в workflow inputs, логи, артефакты или исходный код.

Доступный только в stage служебный маршрут `POST /stage/experiments/fit-lime` принимает `{ "action": "inspect|enable|disable", "profileId": "UUID" }`. Он не включён в обычном production API и не возвращает идентификатор профиля. Перед изменением проверяет роль, карточку тренера и членство в закрытом списке; изменение выполняется в транзакции с блокировкой, число включённых записей не может превысить три.

Для аварийного отката отключить флаг для конкретного пилотного профиля через этот маршрут при доступном stage-контуре либо через контролируемую миграционную операцию в БД. После отключения повторный вход не включает его снова: привязка логина обновляет только `profile_id`, но не `enabled`. Существующая сессия получит новое значение при следующем чтении профиля; до внедрения оболочки в пункте 14 визуальных изменений от флага нет.

Проверка выпуска: для трёх согласованных профилей `fitLime=true`, для непилотного тренера и клиента `false`; после `disable` — `false` после выхода, нового входа и обновления; после `enable` возвращается `true` только у разрешённого профиля. Если личной авторизованной сессии нет, автоматические тесты подтверждают контракт, но проверка реальных учётных записей остаётся отдельным пунктом приёмки. Новый тренер связывается с записью при следующем входе через Яндекс; одна перезагрузка уже открытой сессии не выполняет привязку.
