# Progress AI — устойчивое формирование длинного анализа

Статус: утверждено владельцем продукта 10.09.2026. Разрешены самостоятельная
реализация, PR, merge и production rollout с соблюдением очереди PR.

## Пользовательский результат

Кнопка «Обновить анализ» стабильно создаёт новый человеческий разбор даже на
большой истории тренировок. Одна оборванная или некорректная генерация не
прерывает весь процесс. Пока новый результат не готов, предыдущий анализ
остаётся доступен и не выдаётся за обновлённый.

## Неизменяемый план исправления

### 1. Разделить причины ошибки

Статус: выполнено. Добавлены раздельные коды, безопасные метаданные и тест на
отсутствие текста ответа в логах.

- Отличать некорректный ответ API, ответ модели с остановкой по лимиту,
  некорректный JSON модели и валидный JSON, не прошедший проверку качества.
- Писать в безопасные логи request id, этап, номер части, попытку, статус
  завершения, длину ответа и token usage.
- Не писать в логи текст ответа, тренировочные данные, токены и идентификаторы
  пользователя.

### 2. Исправить обработку больших данных

Статус: выполнено. Части возвращают компактные доказательства, финальный текст
формируется один раз.

- Промежуточная часть возвращает компактные структурированные наблюдения, а не
  полный пользовательский и тренерский тексты.
- Полный человеческий разбор формируется один раз из всех частей.
- Успешно обработанные части не запрашиваются повторно из-за ошибки другой
  части.

### 3. Исправить лимиты и завершение модели

Статус: выполнено. Части ограничены 900 токенами, финальный ответ — 2000;
`TRUNCATED/PARTIAL` обрабатываются до parser.

- Использовать отдельные ограниченные бюджеты для компактной части и финального
  ответа.
- До разбора JSON проверять `AlternativeStatus` YandexGPT.
- Ответ `ALTERNATIVE_STATUS_TRUNCATED_FINAL` или `PARTIAL` считать временной
  ошибкой и повторять, а не передавать в JSON parser.

### 4. Добавить правильные повторы

Статус: выполнено. На каждом этапе действует независимый предел в три попытки.

- Для каждой части и финального ответа выполнять максимум три попытки.
- Повторять сетевые временные ошибки, оборванный ответ, некорректный JSON,
  некорректную структуру и отклонение проверки качества.
- В корректирующий запрос передавать только безопасное описание нарушения; не
  дублировать большой оборванный ответ.

### 5. Сохранить понятное поведение экрана

Статус: выполнено. Контракт pending не менялся, старый анализ сохраняется,
новые ошибки получили отдельные пользовательские сообщения.

- Сохранять существующий pending и блокировку повторного нажатия.
- При исчерпании повторов показывать точную понятную причину.
- Предыдущий успешно сохранённый анализ оставлять на экране.
- Не менять композицию Progress и не добавлять новые действия.

### 6. Проверить качество до выкладки

Статус: выполнено локально. Пройдены 1 379 тестов приложения и 378 тестов API;
отдельный обезличенный сценарий проверяет 45 тренировок и 710 подходов.

- Покрыть тестами truncated/partial status, некорректный JSON, некорректную
  структуру, quality rejection, временный HTTP-сбой и успешный повтор.
- Проверить большой обезличенный сценарий порядка 45 тренировок и 710 подходов:
  разбиение на части, одно финальное формирование и отсутствие повторной
  обработки успешных частей.
- Проверить одинаковый контракт Supabase Edge Function и Yandex Cloud API.

### 7. Выпустить по очереди

Статус: финальный CI. Более ранние #865 и #863 успешно смержены и выкачены;
ветка повторно обновлена от production `main` без конфликтов.

- Запустить целевые тесты и полный `npm run check`.
- Открыть отдельный PR и не сливать его раньше более ранних активных PR.
- После обновления от нового `main` повторить обязательный CI, смержить без
  обхода checks, дождаться обеих функций и production deployment.
- Выполнить HTTP smoke главной, входа и Progress; генерацию с пользовательскими
  данными не запускать без пользовательской сессии.

## Матрица приёмки

| Пункт | Видимый результат | Проверка |
| --- | --- | --- |
| 1 | Ошибка однозначно диагностируется без раскрытия данных | unit-тест лог-метаданных и кодов |
| 2 | Большая история даёт один итоговый разбор | тест chunk → synthesis |
| 3 | Оборванный ответ не попадает в parser | тест AlternativeStatus |
| 4 | Временный дефект исправляется повтором | последовательность mock-ответов |
| 5 | Старый анализ остаётся, ошибка понятна | существующий component test + mapping test |
| 6 | Supabase и Yandex ведут себя одинаково | root/API test suites |
| 7 | Production отвечает после штатного выпуска | CI/CD и HTTP smoke |

## Границы

- Не менять тренировочные записи, цели, замеры, историю и exercise identity.
- Не ослаблять проверку фактов и защиту от выдуманных симптомов.
- Не добавлять deterministic-текст вместо ИИ-разбора.
- Не перестраивать экран Progress.
