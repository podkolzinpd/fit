### Решение SET-STORAGE-01

Причина: существующий coachLiveDensity уже держит failed write в памяти по
аккаунту, time-wheel — по устройству. Применяется тот же ограниченный подход
для пяти указанных предпочтений через маленький локальный storage helper.
Его Map содержит только несохранённые строковые значения старых ключей;
это не новый бизнес-store, repository, серверный state или persistence-формат.
Обычный успешный путь по-прежнему читает localStorage. Успешная запись и
внешний storage event снимают соответствующий transient override; ключи
разных аккаунтов не смешиваются. События существующих hooks сохраняются.
Статус ошибки используется только в настройках тренера. Нельзя выдавать
in-memory значение за сохранённое после полной перезагрузки/закрытия.

Отвергнуты новые cookies/БД/права, глобальный выбор для личных полей,
подавление ошибки без статуса, смена defaults и миграция существующих ключей.
Новые зависимости и флаги не нужны. Параллельные изменения client/CPT/finance
сохраняются; активные старшие main/release/readbacks не прерываются.

Приёмка: unit red/green пяти отказов, recovery и account isolation;
component предупреждения и summary; браузер on/off/reload и storage-error,
320/390/430 и оба движка по затронутым сценариям. Каждый точный source и
фактический main проходят обязательный CI. После публикации — exact assets,
обаAPI, подписи/source/ABI OTA и actualpublic/signedZIP UI. Телефон отдельно;
четвёртый PR только ради приёмки не создаётся.
