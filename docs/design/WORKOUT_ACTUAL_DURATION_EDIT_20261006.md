Поток: product. Базовый main: ba911a31. Один PR, обе роли.

## Принятый план (нумерация и смысл неизменны)

1. **При быстром внесении**

   Сделаем заметное поле «Длительность тренировки, мин» рядом с датой. Например: `50` или `90`. Одинаково для спортсмена и тренера, записывающего тренировку клиента. Поле необязательное: если время неизвестно, можно сохранить без него.

2. **После сохранения**

   В завершённой тренировке покажем «Длительность: 50 мин» и действие «Изменить». Если времени нет — «Указать длительность». Откроется небольшое окно с одним полем и кнопкой «Сохранить», без перехода в редактор упражнений.

3. **Права спортсмена и тренера**

   Спортсмен сможет исправлять длительность своей завершённой тренировки, включая назначенную тренером. Тренер — тренировки доступного ему клиента. Это не должно давать спортсмену право менять сам тренерский план.

4. **Корректное сохранение**

   Введённая длительность будет приоритетнее показания таймера. Дата, упражнения и результаты подходов останутся неизменными. История и связанные расчёты обновятся согласованно. Общую длительность не будем автоматически подставлять вместо времени отдельных кардиоупражнений.

5. **Проверки перед выпуском**

   Проверим создание и последующее исправление у обеих ролей, старые тренировки, тренировки из LIVE, сохранение черновика и работу на телефоне. Отдельно — чтобы ошибка сети или одновременное изменение тренером и спортсменом не затирали данные.

## Контракт реализации

- Переиспользуются actualDurationSec, Field, WorkoutCta,
  modal-dialog и семантические поверхности/типографика FIT.
- /me и /today: только завершённая запись на шаге сохранения; /workouts/new
  и /workouts/:id/edit: общий completed-контур.
- /workouts/:id: отдельное изменение длительности, включая отчёт завершения.
- Единственный primary: «Записать тренировку» в форме, «Сохранить» в диалоге.
- Empty: необязательно; ручной ввод выше Live-таймера. Удаление ручного
  значения возвращает Live-время либо отсутствие значения.
- Pending блокирует повторную отправку/закрытие; error сохраняет введённое;
  conflict перечитывает запись, но не повторяет запись автоматически.
- Narrow API PUT /v1/workouts/:id/duration: только фактическая длительность и
  expectedVersion; actor/session, can_read_workout, done, lock/version.
- Yandex migration 000126, без новой колонки и без Supabase-миграции/dual-write.
- Время запуска/окончания, дата, план, подходы, финансы, награды не изменяются.
- Уже действующие calorie triggers реагируют на actual_duration_sec;
  исходное время отдельных cardio sets сохраняется.
- Состояния обеих ролей: manual/Live/unknown, pending, invalid, network,
  conflict/retry, success. Client 390/430 WebKit, trainer 1440/compact.
- Tracker в предыдущем контексте не настроен: план сохранён в репозитории;
  внешнюю задачу и её статус не выдумываем.

## Окружение и границы доказательства

`npm run local:verify` запущен, но общий локальный PostgreSQL имеет старую историю
миграций: `000111_live_superset_rounds` уже применена до переименования в
`000112_live_superset_rounds`, поэтому повторное создание append_live_round
блокирует эту команду до новой миграции. Общая база и данные не сбрасывались.
Вместо изменения чужой среды создан отдельный task-only Podman PostgreSQL17
на 55434, выполнена чистая цепочка до000126 и все92 actor/RLS теста.
В нём только синтетические fixtures; production данные для тестов не использованы.

Реальные frontend маршруты проверены с Yandex contract fixtures в WebKit;
server validation/session/status errors проверены через Fastify,
авторизация/версии/неизменность aggregate — на настоящем PostgreSQL17.
Production release проверяется отдельно после обязательного зелёного CI/merge.
