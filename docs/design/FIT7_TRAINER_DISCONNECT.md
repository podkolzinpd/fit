# ФИТ 7 — повторная привязка после отключения

Запрос: «Снова карточка клиента, которую отвязал от тренера висит привязанной».
База: `00ee030`, предыдущая попытка исправления — PR #759.

## Подтверждённая причина

`claim_client_invitation` с `target_role=trainer` создаёт `client_trainers`
без `client_trainer_relationships`. Профиль вызывал нетаргетированный
`disconnect_client_trainer`, который возвращал `already_disconnected`,
не удаляя такую запись. Клиентский cache принудительно становился пустым,
но после перезагрузки список возвращал тренера, сохранявшего доступ.
Локальное воспроизведение до исправления: 3/3 проверки выявили дефект.
Связь с конкретной production-карточкой пользователя ещё не подтверждена.

## Исправление

- Профиль использует существующий `remove_client_trainer` для выбранной карточки.
- RPC проверяет владельца через `auth.uid()`, блокирует client row, удаляет
  выбранный membership и закрывает соответствующую активную relationship
  в одной транзакции. Другие тренеры сохраняются. Повтор безопасен.
- Клиентская история и ownership не меняются; legacy root требует миграции
  и по-прежнему не отключается частично.
- Профиль отменяет старую загрузку, убирает только выбранного тренера и
  запрашивает актуальный список, а не скрывает всех тренеров до перезагрузки.
- Старая однопараметрическая RPC остаётся для совместимости; новый UI её не
  использует. Исправление требует deployment frontend и миграции вместе.

## Приёмка

1. Приглашённый тренер отключается, исчезает из fresh server list и теряет доступ.
2. Повторное отключение безопасно.
3. Отключается именно выбранный тренер; остальные остаются.
4. Закрытая relationship сохраняет историю и не блокирует переподключение.
5. Клиент сохраняет данные и доступ; чужой клиент/тренер не может менять связь.
6. Reload и повторный вход: тренер не возвращается, его список клиентов пуст.

Проверки 1–5: 17/17 целевых pgTAP. Изолированный Supabase через Podman:
чистый db reset и все 911 SQL/RLS-тестов (76 файлов) прошли. Свежая генерация
типов подтверждает прежнюю схему и сигнатуру RPC; существующие уточнения
nullable/JSON-типов сохранены, обновлён schema hash. `npm run check`: 1104
frontend, 306 API (29 штатно пропущены), lint/typecheck/build и infra checks
зелёные. Migration safety прошёл. Целевые UI/repository проверки: 37/37.
Проверка 6: добавлен сценарий в `e2e/client-profile.spec.ts`; исполнение ожидается.
Браузерная ручная приёмка (production и localhost) заблокирована runtime:
не удалось проверить административную политику доступа. Ограничение не обходилось.
