# YAFIT-602 — читаемость текста на светлом фоне

Утверждённый план (дословно, синхронизирован с YAFIT-602):

1. В опубликованной версии открыть именно подтверждение архивации цели и записать цвет текста, фон кнопки и номер сборки. В текущем коде кнопка красная, на скриншоте — светлая; без этой проверки нельзя уверенно назвать причину.
2. Задать для опасных кнопок текст и фон одним правилом, убрать отдельное переопределение белого текста. Проверить все диалоги на общем компоненте: архивацию, удаление тренировок и замеров, отключение тренера, отзыв приглашений.
3. Исправить белый текст при выделении на светлой подсветке. Для неактивных кнопок убрать снижение читаемости через прозрачность и задать явные цвета.
4. Добавить проверки фактических цветов элементов, а не только цветовых токенов: светлая и тёмная темы клиента, экраны тренера, обычное и неактивное состояние. Цель — контраст текста не ниже 4,5:1, в том числе у неактивных кнопок.
5. Пройти ключевые экраны и диалоги на мобильной ширине и в iOS Safari, затем выкатить и повторить проверку на опубликованной сборке.

Граница изменения: только CSS и проверки контраста; маршруты, бизнес-логика, сервер и данные не меняются. Для предупреждений, обычных и опасных действий сохраняются действующие подписи, порядок и обработчики. Реальный пользовательский аккаунт для просмотра подтверждения в production не предоставлен — публичная страница входа и её CSS доступны без авторизации. Недоступный авторизованный сценарий необходимо назвать отдельно; нельзя выдавать CSS-fixture за проверку пользовательского аккаунта.

Матрица приёмки: клиент Lime light/dark 390 и 430 px; тренер Lime и Mono 1440 px; обычная/неактивная кнопка, подтверждение, выделенный текст. Для загрузки, пустого состояния и ошибки проверяется отсутствие изменения сценария: подтверждение появляется только после действия пользователя. Для опасных действий охватить общую кнопку подтверждения и вызывающие её сценарии. Итоговые результаты фиксируются ниже после тестов и выпуска.

## Локальная проверка

Публичная `/auth` отдавала CSS `index-uBS7cWPB.css` (сверена только опубликованная таблица стилей, не вычисленный стиль авторизованного окна): в ней клиентское правило задавало опасной кнопке только белый текст, а фон — другое правило. Наблюдавшийся пользователем светлый фон на скриншоте этим одним фактом не объяснён. После правки светлая клиентская тема задаёт красный фон и белый текст одним правилом. Остальные темы сохраняют свой действующий вариант опасного действия.

`e2e/contrast.webkit.spec.ts`: 7/7 в iOS WebKit. Проверены итоговые CSS-цвета и контраст ≥4,5:1 у опасной, обычных и неактивных кнопок, выделения текста; клиент light/dark 390/430, тренер Lime и Mono. В тренерской Lime дополнительно проверены отдельные неактивные кнопки карточки клиента и чата. Скриншоты тестовой матрицы просмотрены; это изолированная CSS-фикстура, не авторизованный маршрут.

`npm run check`: lint, typecheck, покрытие frontend, API, policy/hosting, build — exit 0. Реальный маршрут `/clients/:id/goal` был запущен в локальном Chromium, но авторизация тестового тренера осталась на `/auth` из-за не поднятой локальной базы; сам экран цели этим прогоном не принят. Серверные данные и локальную БД ради визуального исправления не меняли.

Первый CI PR #1538 (37907184856) выявил устаревшее ожидание сценарного теста: пустая неактивная кнопка чата всё ещё сравнивалась с ярким активным фоном. В приложении вычислен новый нейтральный фон и `disabled=true`; тест обновлён проверять именно это состояние и `opacity=1`. Локальный точечный прогон сценария без тестовой базы не дошёл до чата; повторный полный `npm run check` после обновления теста — exit 0. Результат следующего CI коммита фиксируется после завершения.

Остаётся после merge: официальный frontend deployment, readback опубликованного CSS/сборки и повторная проверка доступного публичного маршрута. Проверка самого диалога в production требует авторизованного тестового аккаунта и не подменяется фикстурой.
