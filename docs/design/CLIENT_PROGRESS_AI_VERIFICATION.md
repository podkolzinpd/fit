# Проверка ИИ при пересборке Client Home / Progress

Владелец явно потребовал сохранить качество ИИ в автономно утверждённом плане Home/Progress. Изменения карты не меняют prompt, parser, API или историю пользователей.

Контролируемый workflow `34288992611` на `main` `178094d` проверил реальный разбор «Тестовая тяга Yandex stage, 42,5 килограмма, 10 повторений»: ожидаемые exerciseRef, вес и повторы приняты. Генерация сводки не началась: HTTP 400 `invalid_request`.

Причина — тестовый запрос workflow использовал `clientId/periodStart/periodEnd`, а `readAssistantProgressRequest` и действующий endpoint принимают `client_id/period_start/period_end`. Исправляются только три имени в синтетическом запросе. Регрессионный тест извлекает этот запрос из workflow и передаёт реальному API parser. Production API, модель, RLS, fixture и пользовательские данные не меняются.

PR #830 объединён в main `31113f3afb4540ea229467b801e67d9abb9bcf07` после успешного CI `34289499239`. Повтор штатного live workflow `34291138177` — **success**: реальный parser подтвердил точное упражнение, 42,5 кг и 10 повторений; новая сводка создана (`cached=false`) и найдена через list endpoint после сохранения. Проверялись только synthetic stage fixture и краткоживущая сессия. Это проверка реальной модели/API/сохранения на stage; ручная оценка качества всех ответов и авторизованный production-сценарий пользователя ею не подменяются. Ответы и session tokens не публикуются как артефакты.

Пересборка Client Progress сохраняет защищённый клиентский текст и существующий валидатор подробного анализа. Факты/замеры/цель загружаются независимо от ИИ. Сохранённый анализ показывает собственные даты; карта не заимствует старый период. Явный запрос нового анализа использует существующий force-контракт, сохраняет старый текст при ошибке и привязывает завершение запроса к его клиенту и диапазону дат.

Локально полный npm run check прошёл: 1262 frontend / 364 API / 112 infra, lint/typecheck/build; тест workflow действительно использует API parser.
