# Быстрый старт тренировки на главных экранах — 2026-10-01

Статус: утверждено владельцем; реализация в работе. Поток: `product`.
База: `origin/main` `3dece098`. Общий контракт: один actor-scoped Yandex API/PostgreSQL start-or-resume; Supabase production fallback и новые Supabase migrations запрещены. Основное действие: «Начать тренировку»/«Продолжить тренировку». Референсы: существующие `/me`, стандартный `/today`, пилотный `/today` Schedule V2 и `/workouts/:id/live`; Fit `Page`, `Coachmark`, `WorkoutCta`, `ClientPicker`, `VoiceInputButton`, semantic tokens и SVG-иконки. Вне scope: LLM/SpeechKit, состав существующих планов, новое расписание, глобальная палитра и навигация.

Ниже — исходная нумерация согласованного плана; смысл пунктов не менять без согласования.

1. **Клиент.** Вверху главной — тёмная кнопка «Начать тренировку». Нажатие сразу создаёт пустую начатую тренировку и открывает экран добавления упражнений. Пока она идёт, кнопка становится «Продолжить тренировку». Следом — компактный светлый блок «Составить тренировку» с двумя небольшими кнопками справа: микрофон и клавиатура. Достижения и остальные блоки остаются ниже.

2. **Тренер.** Те же два блока и тот же порядок. «Начать тренировку» на общей главной сначала открывает поиск и выбор клиента; только после выбора начинается пустая тренировка. Из карточки конкретного клиента выбор пропускается. Если у выбранного клиента тренировка уже идёт, открываем её для продолжения, а не создаём вторую. Активные занятия на главной показываем с именами клиентов.

3. **Оба варианта тренерской главной.** Меняем блок действий и на обычной главной, и в уже существующем варианте с расписанием. В последнем календарная сетка и кнопка планирования остаются на своих местах; нового расписания на обычной главной не будет.

4. **Внешний вид.** Новые блоки — белый, графитовый и оттенки серого, без цветных акцентов. Главная кнопка тёмная, блок составления светлый; иконки небольшие, но области нажатия удобны для телефона. Существующие достижения и остальной интерфейс специально не перекрашиваем. В dark theme используются полярные semantic tokens той же геометрии.

5. **Общая логика и проверка.** Старт защищаем от повторных нажатий и создания дублей. Пустое занятие можно продолжить или отменить, но нельзя случайно записать как выполненное. Проверяем клиента и тренера, оба тренерских экрана, отсутствие клиентов, несколько активных занятий у разных клиентов, перезагрузку приложения и ошибки сети.

После этих проверок изменения выпускаются вместе, чтобы два приложения не разошлись по поведению.

## Реализация и защита данных

- Быстрый старт в production работает через один Yandex API/PostgreSQL контракт для обеих ролей. Блокировка карточки клиента сериализует одновременный старт с разных устройств, а `operationId` возвращает результат того же действия после потери ответа.
- Существующую активную тренировку продолжаем вместо создания второй. Подключённый тренер может прочитать и вести занятие, начатое самим клиентом, но не может прочитать или перехватить активное занятие другого тренера. Старт запланированной тренировки и быстрый старт защищены существующим ограничением одной активной тренировки у клиента.
- Новая пустая тренировка не считается выполненной: сервер не разрешает её завершить, интерфейс предлагает добавить упражнение либо отменить пустую запись. Для уже заполненных занятий прежний поток Live не меняется.
- На первом входе клиентская карточка создаётся прежней идемпотентной командой, после чего запускается занятие. Блок составления не запускает Live и сохраняет существующий голосовой/текстовый сценарий.

## Проверки перед выпуском

| Пункт | Подтверждение | Статус |
| --- | --- | --- |
| Клиент: начать/продолжить, тренер: выбор клиента, retry и отсутствие клиентов | Компонентные тесты `QuickStartWorkout` | Локально проверено |
| Запрет дубля, чужого клиента/тренера и пустого завершения | PostgreSQL 17 integration fixture, чистая цепочка миграций | Проверить в CI |
| Обе тренерские главные, мобильный WebKit и light/dark | E2E behavior + visual shards | Проверить в CI |
| TypeScript, сборка, unit и API | `npm run check` | Локально прошло; первоначально sandbox запрещал loopback, повтор с разрешённым локальным тестовым сервером прошёл |
| Production API, frontend и реальный маршрут | Автодеплой после merge и read-only smoke | Не выпускалось |

Локальный Playwright сценарий входа не дошёл до главной: тестовая база авторизации в этой рабочей копии не запущена. Это не результат проверки нового UI; поведенческие и визуальные браузерные гейты оставлены за изолированным CI.

## Матрица состояний до реализации

| Условие | Клиент | Тренер, стандарт | Тренер, Schedule V2 |
| --- | --- | --- | --- |
| Данные есть, активной нет | Старт сразу | Выбор клиента | Выбор клиента над существующей сеткой |
| Активная есть | Продолжить | Старт другого клиента; активные с именами | То же, календарь сохраняется |
| Нет клиентов/карточки | Понятная ссылка на создание своей карточки | Добавить клиента; старт недоступен | Существующий first-client action сохраняется |
| Загрузка | Читаемый pending без создания дублей | Поиск недоступен до списка клиентов | То же; календарь независимо загружается |
| Ошибка чтения | Retry; нельзя запускать вслепую | Retry списка клиентов/тренировок | Независимый retry; календарь не блокирует действия |
| Ошибка mutation/потерянный ответ | Повтор с тем же operation ID | То же после выбора клиента | То же, выбранный клиент сохранён |

## Приёмка

Перед PR заполнить `пункт → видимый результат → тест/скриншот → статус`, отдельно для клиента 390/430 px и тренера в компактном shell и 1440 px; проверить light/dark, WebKit, safe area, focus, длинные русские подписи, пустой Live, быстрые двойные нажатия, чужого/архивного клиента, отсутствие уведомления о запланированной тренировке, reload и retry. Выпуск — только после зелёного полного CI и production smoke.
