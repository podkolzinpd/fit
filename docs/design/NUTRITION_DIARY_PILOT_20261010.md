## Подтверждённый план — дословная копия

Итоговый вариант: **клиент выбирает еду, вводит количество и сохраняет; тренер смотрит тот же дневник в карточке клиента.** Всё остальное — расчёты, источник справочника, хранение и обновления — остаётся внутри системы.

Ниже — план доработок. Пока это план реализации, не выполненные изменения.

## 1. Фиксирую простой сценарий

Основной путь состоит из трёх действий:

**Найти еду → указать количество → сохранить.**

Не требуем анкету, цель калорий, подключение тренера или предварительное заполнение профиля. Не добавляем отдельную вкладку нижнего меню.

В интерфейсе нигде не упоминается Лавка: ни в поиске, ни в записи, ни у тренера. Пользователь работает со справочником еды ФИТа.

## 2. Дорабатываю вход и дневник клиента

В «Кабинете» появляется компактный блок «Питание сегодня»:

- Записанные калории.
- Основная кнопка «Добавить еду».
- Второстепенный переход «Открыть дневник».

Сам дневник:

- Дата сверху: сегодня по умолчанию, стрелки переключения и выбор даты.
- Записанные калории и БЖУ.
- Еда, сгруппированная по приёмам пищи.
- Одна заметная кнопка «Добавить еду».

Не создаём четыре больших пустых блока. Приёмы пищи без записей показываем компактно. При полностью пустом дневнике — короткое сообщение и кнопку добавления.

Числа подписываем **«Записано за день»**, а не «Вы съели»: дневник может быть неполным.

## 3. Делаю добавление еды без лишних экранов

### Экран выбора

Сразу доступны поиск и недавняя еда. Недавние записи включают и продукты справочника, и собственные блюда пользователя.

В результатах:

- Обычное название: «Курица с рисом».
- Калории на 100 г второстепенной строкой.
- Нажатие на всю строку открывает ввод количества.

Не добавляем вкладки «магазины», «каталоги», «бренды» и дополнительные фильтры в первый запуск.

Если ничего не подходит, виден переход «Добавить свою еду». Ошибка поиска не маскируется под отсутствие результатов.

### Экран количества

На одном экране:

- Название еды.
- Поле «Сколько съели, г».
- Рассчитанные калории; БЖУ — рядом, менее заметно.
- Дата и приём пищи компактной строкой.
- Кнопка «Сохранить».

Поле количества сразу готово к вводу с цифровой клавиатурой. Не подставляем произвольный вес как будто пользователь уже его выбрал.

Дата по умолчанию сегодняшняя. Приём пищи берём из места добавления либо предлагаем по времени. Оба значения можно изменить здесь же.

**Не делаем отдельные экраны для даты, приёма пищи и подтверждения.** Нажатие «Сохранить» завершает добавление.

После сохранения возвращаем в дневник на соответствующую дату, показываем новую запись и обновлённый итог.

## 4. Упрощаю ручной ввод и повторение

В ручном вводе сразу показываем только:

- Название.
- Калории съеденной порции.
- «Сохранить».

БЖУ раскрывается по желанию. Для ввода по этикетке есть отдельный переключатель «На 100 г»: тогда добавляется поле съеденного веса.

Не заставляем пользователя заполнять неизвестные значения.

Повторное использование:

- Недавняя еда доступна сразу при добавлении.
- При выборе прошлой записи подставляется прошлое количество, которое можно исправить.
- Новая запись сохраняется только после нажатия пользователя.

В дневнике нажатие на запись открывает редактирование. Удаление — второстепенное действие с возможностью отмены. Не выносим рядом несколько одинаково заметных кнопок.

## 5. Делаю справочник понятным и расчёты устойчивыми

Во внутреннем справочнике сохраняем название, КБЖУ и основу расчёта. Торговые сведения в пользовательские данные не переносим.

При подготовке:

- Очищаем названия от магазинных и рекламных обозначений.
- Проверяем единицы и заполненность.
- Не объединяем автоматически разные блюда только по совпадению названия.
- Существенные различия объясняем обычными словами: например, «Рис варёный» и «Рис с маслом».

Общие блюда имеют ориентировочное КБЖУ. Короткое пояснение об этом размещаем в подробностях продукта, не повторяем длинное предупреждение на каждом экране.

Для количества используем граммы либо миллилитры — в зависимости от основы расчёта. Кнопок «Вся упаковка» и «Половина упаковки» нет.

Старые записи сохраняют свои исходные значения и не меняются при обновлении справочника. Неизвестное БЖУ не считается нулевым.

## 6. Добавляю питание в карточку клиента у тренера

Путь: **«Клиенты» → карточка клиента → «Питание»**.

Компактный блок рядом с историей тренировок и прогрессом:

- Записанные калории и БЖУ за сегодня.
- Количество записей.
- Время обновления.
- «Открыть дневник».

Блок не перехватывает главное действие карточки — работу с тренировками.

В дневнике тренер:

- Переключает даты.
- Видит еду, количество и КБЖУ.
- Открывает подробности записи.
- Переходит в существующий чат для обсуждения.

Просмотр без редактирования. Никаких сведений о магазине или источнике данных.

Если сегодня нет записей, показываем именно это. Последний заполненный день можно открыть отдельной ссылкой с явной датой.

## 7. Делаю доступ и ошибки простыми для пользователя

В дневнике клиента — настройка «Доступ тренеру». Один переключатель для конкретного подключённого тренера и короткое объяснение: он увидит сохранённую историю, но не сможет её менять.

По умолчанию доступ закрыт. При отключении или смене тренера разрешение не переносится автоматически. Проверки выполняются на сервере для каждого чтения.

Состояния интерфейса различаются:

| Ситуация | Что показываем |
|---|---|
| Нет записей | Предложение добавить еду |
| Нет доступа у тренера | Объяснение, что разрешение даёт клиент |
| Ошибка загрузки | «Повторить», без ложных нулей |
| Ошибка сохранения | Сохранённый черновик и повторная попытка |
| Неполное БЖУ | Пометка о неполных данных |

Повторное нажатие не создаёт дубль. Выход из аккаунта очищает личные данные из интерфейса. Для дневника выбираем один основной контур хранения, чтобы история не раздваивалась.

## 8. Что сознательно не добавляю в первый запуск

Чтобы сохранить простой UX, откладываю:

- Обязательную отметку «За день всё записано».
- Отдельное избранное — сначала достаточно недавней еды.
- Графики, оценки рациона и недельные средние.
- Нормы калорий и автоматический «остаток».
- Фото еды, рецепты и сканирование штрихкодов.
- Уведомления тренеру о каждом добавлении.

Отметку завершённости дня можно добавить позже как необязательное действие, если пилот покажет её пользу. В первом запуске явно обозначаем, что итог отражает только записи.

## 9. Порядок работ и приёмка

1. Подготовить проверенный справочник и выбрать хранение.
2. Реализовать записи, расчёты и права доступа.
3. Сделать клиентский сценарий: добавление, история, повторение, исправление.
4. Добавить сводку и просмотр у тренера.
5. Обновить навигацию и помощника приложения.
6. Проверить сценарии и провести небольшой пилот.

Проверяю не только расчёты, но и удобство: маленькие экраны, экранную клавиатуру, читаемость, доступность кнопок и возврат назад без потери ввода.

Критерии приёмки:

- Новый пользователь добавляет еду без объяснений со стороны команды.
- Для продукта из справочника обязательно вводится только количество.
- Повторная запись не требует заново вводить название и КБЖУ.
- Клиент и тренер видят одинаковые разрешённые записи.
- Ошибки не теряют ввод и не создают дубли.
- Посторонний пользователь не получает дневник.
- Магазинная информация отсутствует во всём интерфейсе.

## Оценка как UX-дизайнер

**План — 9/10. UX-концепция — 9/10.** Это экспертная оценка структуры, пока не результат пользовательского тестирования.

Что хорошо:

- Один короткий основной сценарий.
- Минимум обязательного ввода.
- Привычное расположение внутри существующих экранов.
- Быстрое повторение повседневной еды.
- Понятное разделение действий клиента и тренера.
- Нет лишних настроек, графиков и торговой информации.

Главные риски: человеку может быть сложно оценить вес порции, а общее название блюда не гарантирует совпадения состава. Поэтому ввод количества должен быть особенно удобным, а справочные значения — честно обозначенными.

**До 10/10 не хватает наблюдения за реальными пользователями:** где они задерживаются, ошибаются с количеством и не находят свою еду. После пилота дорабатываем именно эти места, а не добавляем функции ради количества.

## Согласованное изменение источника — 10.10.2026

Пользователь: «ок, бери вкусвилл, фиксируй план, делай, выкатывай».

Источник названий и КБЖУ заменяется на официальный публичный MCP ВкусВилла: <https://mcp.vkusvill.ru/mcp>. USDA и перевод зарубежного справочника не входят в эту реализацию. Исходный план выше сохранён дословно; меняется источник данных, а не клиентский или тренерский сценарий. Запрет торговой информации в интерфейсе распространяется на любой магазин, включая ВкусВилл.

### Подключение и качество данных

1. Сервер Fit использует только чтение: `vkusvill_products_search` и `vkusvill_product_details`. Поиск запрашивает минимальные поля `id`, `name`, `properties`. Цены, фото, ссылки на магазин, наличие и рекламные описания не передаются в клиентский справочник. OAuth, корзины, заказы, адреса доставки и магазинные аккаунты пользователей не нужны.
2. В собственную модель попадают внутренний идентификатор источника, обычное название, энергия, белки, жиры, углеводы и явно указанная база расчёта. Технический источник остаётся на сервере. Очистка названия сохраняет различия блюда, способа приготовления и состава; одинаковое общее название не означает одинаковые КБЖУ.
3. КБЖУ проверяются по свойству пищевой ценности, а не вычисляются из веса упаковки. Поддерживаются десятичные точка/запятая и проверка единиц; отсутствие значения остаётся `null`, а не нулём. HTML из источника не отображается и не исполняется. Некорректные, неоднозначные или неподдерживаемые данные не заполняют форму автоматически.
4. Несколько изготовителей с разными КБЖУ нельзя усреднять, выбирать по первому совпадению или объединять. Пока нет однозначного значения для продукта, он не предлагается как проверенный вариант с автоматическим расчётом. Ручной ввод из исходного плана остаётся доступным.
5. При сохранении записи сервер фиксирует снимок названия и значений. Обновление источника не пересчитывает прошлые дни. Недавняя еда доступна из собственного дневника и не зависит от доступности магазина.
6. Для пилота не выполняется массовая выгрузка каталога. Поиск ограничивается запросами пользователя, с задержкой ввода, ограничением частоты, таймаутом и различимыми ошибками/пустыми результатами. Клиентская история и ручное добавление не должны блокироваться при отказе внешнего сервиса. Опубликованные лимиты и допустимость хранения/повторного использования нужно подтвердить перед выпуском; доступность публичного API сама по себе не доказывает наличие лицензии на перепубликацию базы.

### Проверенные факты, не статус реализации

- Официальная документация: <https://mcp.vkusvill.ru/mcp>; официальный манифест: <https://github.com/vkustech/vkusvill-mcp-server-manifest>.
- Live-проверка публичного поиска и карточки без учётных данных вернула реальные значения. Для «Курица в сливочно-шпинатном соусе с рисом», id `120063`: 152,2 ккал, Б 9,8 г, Ж 4,2 г, У 18,8 г на 100 г. Это проверенный образец, а не подмена всего справочника одной фикстурой.
- У «Рис с куриной бризолью», id `67492`, ответ содержит три различных набора КБЖУ изготовителей. Обязательный негативный тест: никакого автоматического выбора/усреднения.
- Отказ старого внутреннего доступа больше не препятствует исследованию нового источника. Условия использования данных, точные лимиты, интеграция, тесты и выпуск пока не подтверждены.

### Последовательность реализации и включения

Все девять пунктов исходного плана остаются обязательными. Сначала адаптер источника и проверки нормализации; затем миграции дневника, снимки и права/согласия; клиентские экраны; тренерская карточка и read-only дневник; навигация; ролевые, расчётные и визуальные проверки; штатный выпуск с независимым закрытым флагом. Включение — только для пяти ранее указанных и подтверждённых профилей: три клиента, два тренера. Новое разрешение на просмотр дневника клиент даёт сам; включение пилота его не подменяет.

## Дополнение: технический preflight и границы публикации

- Клиент: `/me/nutrition?date=YYYY-MM-DD`; тренер: `/clients/:clientId/nutrition?date=YYYY-MM-DD`. Новая вкладка нижнего меню не появляется.
- UI: существующие `Page`, `AsyncView`, `Field`, `Switch`, `SaveStatus`, `useConfirm`, `OverflowMenu`, `Coachmark`, иконки и токены текущего Fit. Кабинет остаётся voice-first; блок питания второстепенный. На экране добавления главное действие — сохранение.
- Loading, empty, error, saving, read-only, no-consent, incomplete-macros — отдельные состояния; ошибка не считается пустым дневником.
- Дата и маршрут находятся в URL, формы в React Hook Form, серверные данные в существующем data-backend и TanStack Query. UI не ходит прямо к источнику.
- Независимый default-off флаг питания. При неполном/невалидном составе пилота входы и прямые маршруты закрыты. Сервер проверяет свою когорту независимо от фронтенда.
- Идентификаторы пяти профилей должны быть подтверждены штатным контуром; совпадение имени, префикса email или участие в другом пилоте не является подтверждением.
- Доступ привязывается к конкретной актуальной связи клиента с тренером. Отключение, повторное подключение или смена тренера не наследуют старое разрешение.
- Никаких новых email, push, покупок, импорта заказов, автоматических сообщений или диетологических рекомендаций.
- Реальные КБЖУ не заменяются выдуманными seed-данными. Тестовые фикстуры используются только в тестах.
- Перед включением: проверенный реальный справочник и допустимость его использования; actor/RLS и API-тесты; оба ролевых интерфейса; 390/430 px клиент, 1440 px тренер, узкий экран, две темы, ввод и возврат; зелёные проверки; штатные миграции; сравнение опубликованного bundle; свежая native-сборка.

## Проверенные внешние ограничения

- 10.10.2026: старый внутренний доступ к каталогу завершился `YtProxyUnavailable`; это не проверка доступности HTTP API. Пользователь выбрал ВкусВилл; публичные поиск и карточка нового источника проверены на реальных данных. Старый блокер доступа не переносится на новый источник.
- 10.10.2026: GitHub-переменная `VITE_COACH_WORKOUT_REDESIGN_PILOT_USER_IDS` отсутствует; использовать чужую когорту или предполагаемые UUID нельзя.
- Репозиторий публичный. Пользовательские email не публикуются в плане, issue, коммитах, скриншотах и артефактах CI.
- 10.10.2026: автоматическая проверка безопасности отклонила создание GitHub-тикета с этим внутренним планом в публичном репозитории. Тикет не создан; повторные/обходные попытки не выполняются. Для публикации плана требуется отдельное разрешение владельца на публичное размещение или приватное место фиксации.
- Дословная локальная фиксация и отдельное согласованное изменение источника завершены; на момент фиксации продуктовый код, миграции, commit/PR и deployment не выполнены. После уточнения владельца обязательным местом задачи является YAFIT; доступ и отсутствие обязательных форм проверены, совпадающей задачи по поиску питания/КБЖУ/дневника не найдено. GitHub issue #1559 не заменяет этот гейт. Остальные гейты полного плана остаются обязательными.

## Промежуточные доказательства реализации

- Миграция `000141_nutrition_diary.sql` применена вместе с полной текущей цепочкой в отдельной локальной PostgreSQL 17 для этой задачи. Production и чужие локальные базы не изменялись.
- Полный `actor-context.integration.test.ts`: 139 тестов прошли, включая питание. Проверены собственные записи без предварительной карточки, повтор сохранения без дубля, конфликт версии, редактирование, удаление/восстановление, независимая когорта, разделение ролей, согласие отдельно каждому тренеру, отзыв и отсутствие наследования при повторном подключении. Добавлены проверка последнего записанного дня и транзакционная проверка Down/Up миграции с восстановлением минимальных прав и RLS.
- Целевые тесты адаптера, доменных входных данных и HTTP-границы: 44 прошли. HTTP-проверки покрывают недействительные/двойные/read-only credentials, отключённый сервис, отсутствие подмены владельца через body, невалидные запросы, закрытый тренерский дневник, безопасные ошибки, ограничение частоты и отсутствие поиска/даты/UUID/тела/credentials в request logs. Полный API check прошёл: 1316 тестов, 139 DB-тестов отдельно выполнены, lint/typecheck/build зелёные. Это не полная продуктовая/UX-приёмка.
- Клиентские и тренерские экраны реализованы. Входы в кабинет/карточку используют публичный контракт feature, два отдельных Coachmark; роль/прямой маршрут закрыты вне независимой когорты. Полная UX-приёмка, реальные идентификаторы пяти профилей, CI/release и опубликованный bundle/native ещё не завершены. Ни один пункт исходного плана не снят.
- 7/7 изолированных WebKit-сценариев прошли на синтетических аккаунтах: обе темы, 320/390/430 px, черновик при возврате и reload, потерянный success-ответ после commit и повтор с одним UUID, редактирование/удаление/возврат/повтор, собственная еда с `null` БЖУ и исправлением калорий, пустой поиск отдельно от отказа источника, grant/revoke, тренерский read-only 1440 px и запрет маршрута вне когорты. Отдельно проверены сводка тренера с количеством и временем обновления и явно датированная ссылка последних записей. Поля выбора имеют высоту не менее 48 px; оба утверждённых YS Geo начертания загружены перед скриншотами. Скриншоты хранятся вне публичного git в `outputs/nutrition-diary-pilot-20261010/acceptance-final/`. Это браузерная проверка, не физический iPhone.
