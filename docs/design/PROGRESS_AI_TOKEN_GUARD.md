# Progress AI — ограничение расхода токенов

Статус: утверждено владельцем продукта 12.09.2026, в работе.

## Пользовательский результат

Неизменные данные и повторные открытия Progress не расходуют токены модели.
Для одного нового состояния данных выполняется не более одного платного вызова,
в том числе при нескольких вкладках и экземплярах serverless-функции. Старый
успешный анализ остаётся доступен при ошибке новой генерации.

## Неизменяемый план

### 1. Закрыть повторные платные запросы

- Использовать единый fingerprint в обоих контурах.
- Включить в него данные, период, модель, версию промпта и агрегатора.
- Всегда проверять кеш независимо от `force`.
- Кнопка «Обновить» при неизменных данных должна возвращать сохранённый
  результат: 0 токенов.

Статус: в работе.

### 2. Сделать общую блокировку в БД

Создать запись генерации с уникальным ключом `client + period + fingerprint`.
Первый запрос получает право вызвать модель. Все остальные получают готовый
результат либо состояние «анализ формируется», но модель повторно не вызывают.
Механизм должен работать между разными экземплярами облачной функции.

Статус: в работе.

### 3. Ограничить генерацию одним обращением к модели

- Максимум один платный AI-вызов на fingerprint.
- Убрать автоматический AI-repair.
- Безопасные стилистические нарушения исправлять обычным кодом.
- При плохом ответе сохранять предыдущий анализ, а не запускать модель повторно.

Статус: в работе.

### 4. Ввести кеш ошибок

Если определённый fingerprint уже получил ошибку качества, не повторять запрос
автоматически, установить паузу 30 минут и пропускать сразу новый fingerprint
после изменения тренировочных данных.

Статус: в работе.

### 5. Остановить фоновые перезапуски на экране

Для запроса генерации отключить автоматический retry, повтор при возвращении во
вкладку, повтор при восстановлении интернета и повторный запуск после remount.
Один выбор периода — максимум одна проверка кеша.

Состояния: сохранённый анализ остаётся виден во время проверки и при ошибке;
pending блокирует повторное нажатие; пустой период запускает одну проверку;
ошибка допускает только явный повтор после серверного cooldown.

Статус: в работе.

### 6. Уменьшить агрегат без потери каталога упражнений

- Все упражнения оставить в компактном реестре.
- Подробные контрольные точки передавать только для 15–20 наиболее значимых
  движений.
- Удалить повторяющиеся поля, `null` и дублирование предыдущего периода.
- Целевой предел: 15–20 тысяч символов вместо наблюдавшихся 39,8 тысячи.

Статус: в работе.

### 7. Добавить жёсткий бюджет

- Максимум один вызов для одного fingerprint.
- Не более трёх новых анализов клиента в сутки — по одному на каждый период.
- Ограничить вход 20 тысячами символов.
- Ограничить ответ 1 000 токенов.
- Добавить аварийный выключатель генерации.

Статус: в работе.

### 8. Сделать расход полностью наблюдаемым

Записывать для каждого обращения fingerprint, cache hit, подавленный дубль,
количество вызовов модели, input/output/total tokens, неуспешные ответы и
причину повторного запроса. Персональные данные и тексты анализов в логи не
писать.

Статус: в работе.

## Ожидаемый результат

| Сценарий | До исправления | После исправления |
| --- | ---: | ---: |
| Повторное открытие без новых данных | иногда платный запрос | 0 токенов |
| Ручное обновление без изменений | иногда платный запрос | 0 токенов |
| Новый анализ | примерно 18–25 тыс. токенов | примерно 7–11 тыс. |
| Три неудачные попытки | примерно 55–75 тыс. | не более 7–11 тыс. |
| Снижение относительно проблемной серии | — | около 80–90% |

## Границы

- Качество и стиль текста анализа в этой задаче не улучшаются.
- Production-тренировки, замеры, цели и старые анализы не переписываются.
- Автотесты используют только mock-ответы и не обращаются к live AI.
- Production-проверка не создаёт платный smoke-запрос: проверяются rollout,
  health и кеш уже существующего анализа.
