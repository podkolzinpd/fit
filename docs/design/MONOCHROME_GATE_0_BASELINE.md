# Fit — Gate 0: инвентаризация и baseline

Статус: **Gate 0 принят 2026-08-29**.

Дата инвентаризации: 2026-08-29.

Эта задача ничего не меняет в интерфейсе. Она фиксирует реальный Client Home,
текущее устройство тем, визуальный долг и набор состояний, который должен быть
защищён до первого продуктового пилота.

## Решение Gate 0

Первым пилотным экраном остаётся **Client Home**.

- Канонический маршрут: `/me`.
- Роль: `client`.
- Реальная цепочка: `MyClientPage → TodayPage(clientMode) →
  ClientHomeOverview`.
- Shell: `AppLayout`, `.phone-frame`, `.content`, `.client-tab-bar`.
- Экран уже имеет стабильные fixture-данные, unit-проверки и визуальные
  baseline на 390 и 430 px.
- На нём одновременно видны типографика, primary/secondary/ghost actions,
  карточки, данные, навигация, empty/first-run, loading/error и обе темы.

Client Home подходит для проверки всей новой айдентики. Начинать с другого
экрана причин не найдено.

## Граница будущего пилота

В Gate 3 входят:

- page shell, заголовок «Сегодня», приветствие и аватар профиля;
- voice-first действие «Надиктовать тренировку» и «Ввести текстом»;
- first-run для клиента без тренировок;
- следующая, сегодняшняя, активная и просроченная тренировка;
- недельная регулярность;
- один highlight: ответ тренера, личный рекорд или цель;
- retryable error;
- install prompt;
- нижняя клиентская навигация;
- Wearable-карточка только для реально включённого пилотного сценария.

Не входят:

- раскрытый текстовый composer, review и save flow — задача 13;
- карточка тренировки и история упражнения — задача 14;
- Live — задача 15;
- Progress, профиль и список тренировок — их собственные экранные задачи.

На `/me` эти сценарии могут открываться без смены route. Route-scoped preview
должен поэтому опираться не только на pathname, но и на границу Home-состояния,
чтобы раньше времени не перекрасить composer/review/save.

## Защищаемый baseline перед Gate 3

Перед изменением Client Home нужно получить сравнимый before-набор. Полный
review-набор снимается на 390 и 430 px, в light и dark. В committed visual
regression остаются стабильные представительные состояния, остальные
проверяются детерминированными component/e2e assertions.

Минимальный визуальный набор:

1. `H03` — first-run и voice-first действие;
2. `H05` — сегодняшний план, неделя и цель;
3. `H06` — активная тренировка и единственный filled primary;
4. `H07` — будущий компактный план и install prompt;
5. `H08 + H12` — прошлый план и ответ тренера;
6. `H13` — личный рекорд;
7. `H14` — реальная retryable error;
8. `H16` — восстановление draft без потери главного действия.

Дополнительные component captures:

- `H01/H02` — `AsyncView` loading/error уровня профиля;
- `H09` — загрузка недельной регулярности;
- `H15` — реальные фазы voice-кнопки;
- `H18` — Wearable только при включённом allowlist.

Если fixture не может воспроизвести состояние через существующую логику, оно
не добавляется как искусственная картинка: сначала подтверждается, что это
реально достижимый продуктовый сценарий.

## Текущее устройство тем

Сейчас существуют две независимые пользовательские темы и один старый вариант:

- `light` → `.theme-light`, текущая коралловая light palette;
- `dark` → базовые `:root` значения, текущая тёмная coral palette;
- `dark-pilot` → `.theme-dark-pilot`, прежний фиолетовый эксперимент для
  default-off allowlist.

`dark-pilot` не является новым монохромным дизайном и не должен быть
переиспользован. Новый identity-preview обязан быть отдельной осью от
пользовательского выбора `light / dark`.

## Инвентаризация токенов

Аудит `src/styles.css` на момент Gate 0:

- 155 объявленных CSS custom properties;
- 463 вхождения hex-цветов, 302 уникальных значения с учётом alpha-вариантов;
- после основных theme-блоков остаётся 101 вхождение и 74 уникальных literal
  цвета в component/theme override правилах.

Числа — baseline технического долга, а не требование механически удалить все
цвета. Допустимые semantic literals после миграции должны жить в theme tokens,
SVG assets или документированном data-series contract, а не внутри локального
компонентного правила.

### Пересекающиеся группы

| Группа | Текущие токены | Риск для редизайна |
| --- | --- | --- |
| Foundation | `--bg`, `--fg`, `--surface*`, `--border`, `--input`, `--hairline` | четыре близких surface-роли используются непоследовательно |
| Brand/accent | `--accent*`, `--on-accent`, `--selection` | коралловый/фиолетовый связан одновременно с CTA, ссылками, focus и декором |
| Voice aliases | `--voice-*` | дублируют foundation и accent; могут сохранить coral через alias |
| AI aliases | `--ai-*`, `--client-ai-*` | много отдельных градиентов, border и shadow значений |
| Semantic | `--success*`, `--warning*`, `--danger*`, `--live-indicator*` | смысловые цвета нужно сохранить, но отделить от бренда |
| Navigation/shell | `--frame-*`, `--bar-bg`, локальные `.tab-bar` literals | нижняя навигация частично обходит токены |
| Geometry/type | `--radius-*`, `--space-*`, `--type-*`, `--text-*` | Client Home часто использует локальные px вместо этих ролей |

### Прямой долг, видимый на Client Home

- `.tab-bar` содержит локальные coral/dark/neutral literals и отдельные
  light/dark overrides.
- `.today-profile-avatar`, ссылки недели и прошлых планов используют
  `--accent-*`, поэтому автоматически наследуют старый coral/purple.
- `.today-greeting` ссылается на необъявленный `--text`; фактический цвет
  получается через CSS inheritance, а не через явный контракт.
- размеры текста заданы локальными `12/13/14/15/17/20/25–32px`, несмотря на
  существующую шкалу `--type-*`.
- spacing и радиусы используют локальные `7/9/13/14/15/18/20/22px` и pill
  `99px`; их нельзя перенести в новый стиль механической заменой цвета.
- active-card использует локальный gradient из semantic success surface.
- стрелки перехода `›`, check `✓`, приветствие `👋` и реакции `👍/🔥/💪`
  смешаны с Fit SVG-иконками. В Gate 2/3 нужно отдельно решить, что остаётся
  содержательной реакцией, а что заменяется системной иконографикой.
- expanded composer на том же `/me` содержит прямой coral `#F26B4A`; он не
  входит в Gate 3 и не должен случайно измениться вместе с Home.

## Инварианты для before/after

При редизайне Client Home нельзя менять:

- маршрут `/me`, роли и права;
- порядок voice-first действий;
- приоритет active workout над планами;
- filled primary только для «Продолжить» активную тренировку;
- выбор одного highlight с приоритетом feedback → record → goal;
- отсутствие недельного блока при нулевом результате;
- тексты, метрики, ссылки и retry-поведение;
- нижнюю информационную архитектуру из четырёх разделов;
- доступность всех состояний и 44 px target там, где он уже требуется.

## Критерий приёмки Gate 0

Gate 0 можно принять, если команда подтверждает:

1. `/me` — первый продуктовый пилот;
2. граница Home не захватывает composer/review/save;
3. перечисленные `H01–H18` являются реальными состояниями и не требуют
   искусственного UI;
4. минимальный before-набор достаточен для сравнения;
5. старый `dark-pilot` остаётся отдельным от monochrome identity-preview.

После принятия можно переходить только к Gate 1, задаче 2 — Onest и компактной
типографике в изолированном component preview. Feature-экраны при этом ещё не
меняются.

## Проверка baseline

- `ClientHomeOverview`, `FirstRunExperience`, theme и feature flags: **45/45
  unit-тестов прошли**.
- Существующие PNG baseline для Client Home 390/430 и будущего плана найдены,
  размеры и содержимое проверены.
- Runtime-сверка четырёх Playwright screenshots запущена, но не дошла до
  сравнения: локальный Supabase не стартовал, потому что Docker daemon на машине
  выключен. Все четыре сценария остановились на auth `/auth`; это не
  screenshot mismatch и не визуальная регрессия.
- Штатная подготовка `npm run local:prepare` не сбрасывала и не меняла облачные
  данные; она также остановилась до запуска базы.

Перед Gate 1 runtime-сверку можно повторить после запуска Docker Desktop. Для
приёмки самой инвентаризации отсутствие локального backend не меняет найденные
маршруты, состояния, CSS-токены или существующие committed baseline.

Обязательное условие выпуска: до приёмки первого Gate с визуально изменённым
интерфейсом локальный runtime должен быть восстановлен и должна пройти реальная
Playwright before/after сверка. Наличие committed PNG и unit-тестов не заменяет
эту проверку после появления визуальных изменений.
