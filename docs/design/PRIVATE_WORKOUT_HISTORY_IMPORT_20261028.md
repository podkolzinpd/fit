## Этап 1: проверка существующего

База: main a612842a3d38b2600b213e506ef13479883b3d03.
Уже есть: save_completed_workout и штатные доменные команды, actor/RLS,
read-only operational workflow и секретные параметры предыдущей диагностики.
Переиспользуем: отдельную owner read-only и runtime read-only connections.
Меняем: только opt-in диагностику одной новой цели; никакого apply в этом PR.
Не проверено: реальное совпадение тренера, точная карточка, дубли, возможность
сохранить весь неполный журнал без выдуманных параметров.

Предыдущие FIT_ACCOUNT_HISTORY_TARGETS/EVIDENCE не меняются. Новый secret
FIT_WORKOUT_HISTORY_TARGET содержит только trainerLoginSha256/trainerEmailSha256/clientNameSha256;
значения не публикуются. Workflow workout_history_target=true требует main,
доверенный runner, общий VM lock; несовместим с account_history=true. Поиск
принимает только точные hashes, не SQL/actor override/свободный запрос.
В выводе только булевы результаты и количества. При двух активных карточках
ничего не выбирается и запись не разрешается. Клиентские данные не экспортируются.

Этап не меняет API, БД, UI, флаги и конфигурацию моделей; runtime/frontend/native
переиздавать ради read-only проверки не требуется. Новый этап записи может
начаться только после фактического P3/P4 и проверки сохранения на локальных
синтетических данных. Штатная очередь PR и зелёный CI сохраняются.

Проверки этапа1:46/46 operational и8/8 scope tests; полный npm run check
пройден. Отдельная одноразовая локальная PostgreSQL17: чистая цепочка migrations,
синтетическая действующая связь без private membership находится через fit_api,
после отключения связи карточка скрыта. Тестовая база удалена; пользовательские
данные в репетицию не передавались. Целевые тесты повторяются после уточнения
SQL-фильтра действующей связи; полный набор не повторяется без нового сигнала.

Для Яндекс ID логин и почта проверяются раздельно: текущий auth-контракт
хеширует identity.login, тогда как legacy registry сопоставляется по email.
Preflight принимает три приватных hash и проверяет оба login-варианта на
неоднозначность. Это только чтение соответствий; auth и настройки не меняются.

## Независимость read-only диагностики от общего мониторинга

Первый production запуск40741465083 не дошёл до preflight: общий мониторинг
вернул ошибку фонового worker (push/prepare, SQLSTATE22023), и default-success
условие пропустило последующие шаги. Это не результат поиска учётки; чтение
карточки и запись журнала не выполнялись. Сам worker этой задачей не меняется.

Для явно запрошенного workout_history_target диагностический шаг выполняется
через always(), сохраняя main/host/READ ONLY/role/secret guards. Прежний
account_history по-прежнему требует success(). Общий мониторинг продолжает
возвращать failure при сбое; continue-on-error не добавляется. Это доступность
обезличенной read-only диагностики, не обход CI, readiness или разрешение apply.

## Уточнение цели после read-only проверки

Это не доказывает отсутствие карточки: у неё может быть другое имя или найден
прежний профиль. Владелец разрешил создать новую карточку. Это заменяет поиск
существующей карточки в P3; существующие карточки, истории и финансы не менять.

два булевых признака; не публикует identity, email, ID или содержимое сессий.
Legacy email без подтверждённого текущего входа не разрешает запись.
Если профиль не связан с Yandex ID, запросить актуальный ID профиля тренера.
Новый инструмент записи и перенос всех данных остаются следующими пунктами
P5/P6, не результатом этой диагностической правки.

Решения по P2 сохранены приватно: четыре движения исключены, восемь названий
