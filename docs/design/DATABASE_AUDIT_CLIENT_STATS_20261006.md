# Статистика карточки клиента без полной истории

Карточка `/clients/:id` получает итоговые значения статистики одним запросом
Yandex API, без загрузки упражнений и подходов для этого расчёта. Показатели,
права доступа, оформление и поведение ошибок сохраняются.

## Подтверждённый план

1. Найти расчёты, которым достаточно итоговых значений.
2. Перенести их в SQL-агрегаты на API, не передавая всю историю.
3. Проверить совпадение результатов, разграничение доступа и пустые данные.

Уточнённый scope — только обычная статистика карточки клиента. Генерация
ИИ-анализа, Assistant, «Прогресс», данные упражнений и ближайшие назначения
не меняются. Запрос ближайших назначений в карточке пока отдельно читает
историю; этот PR устраняет повторное чтение ради статистики, а не все
чтения истории на экране.

## Контракт

Поток data-media, базовый main `f4bcc188`, зависимости #1450/#1452 уже слиты.
`workouts.clientStats(clientId, today: LocalDate)` возвращает существующий
`ClientStats`. Yandex implementation — `GET /v1/clients/:clientId/workout-stats`
с календарным `today` в часовом поясе actor. Ответ содержит только пять
показателей, `Cache-Control: no-store`; транспорт остаётся в queries.
HTTP-лог нового endpoint сохраняет только шаблон операции, без client ID,
query-параметров и session headers; это покрыто API regression test.

Сервер читает `public.clients` и `public.workouts` одним SQL-запросом в actor
transaction. Недоступный клиент не превращается в пустую статистику. RLS
автора тренировок сохраняется: тренер видит свои назначения, клиент — свои
доступные тренировки. Схема, grants, migrations и роли не меняются.

Завершённые тренировки считаются по `status=done`, без проверки полноты плана.
Знаменатель процента — завершённые, отменённые и прошлые planned; текущие и
будущие planned не входят. Округление до целого сохраняется. Удалённые записи
исключены, внимание наступает через 14 календарных дней без завершённой
тренировки. Пустая история возвращает ноль и nullable даты/процент/дни.

Legacy local adapter оборачивает прежние `listSummaries`/`computeClientStats`;
новых Supabase запросов, migrations и production fallback нет.

## Приёмка

1. Расчёт выбран: только `client-stats` в ClientDetailPage; ИИ и Progress
   не используют новый endpoint. Сохранены Page, AsyncView,
   ClientDetailSourceState, QuickStartWorkout и существующие токены; primary
   «Запланировать тренировку» не меняется.
2. API и repository реализованы: один агрегат, без workout DTO/children;
   repository contract test проверяет отсутствие training-data вызова.
3. Целевые проверки: repository46/46, API227/227, локальный PostgreSQL17
   actor/RLS85/85, WebKit13/13 и Chromium13/13, включая карточку на390/1440 и независимый retry.
   `npm run check` прошёл: lint/typecheck, frontend2380/2380,
   API1094/1094 и build;85 DB-тестов в общем запуске skipped, отдельно85/85.
   Финальный CI остаётся гейтом перед передачей PR.

Тесты покрывают больше100 тренировок, пустую историю, soft delete, границу
внимания, будущий план, cancelled, in_progress, root/member/client/outside
доступ, validation календаря/UUID, несовместимые и истёкшие сессии, отказ БД
и повтор. WebKit читает реальный маршрут на локальной HTTP-fixture, не
production. Физическое устройство и production rollout здесь не проверены.

`local:verify` имеет прежний независимый блокер исторической Supabase
миграции; новую схему этот PR не вводит. Сброс baseline не выполняется.
Tracker в доступном контуре не настроен; чеклист сохраняется в Git и PR.
