# YAFIT-578 — дробная дистанция

Поток: product, с расширением Yandex-схемы. База после выпуска #1322:
`8059c68a` (`origin/main`).
Результат: спортсмен и тренер могут вводить десятые и сотые метра либо километра
в плане, ручном результате и Live; ранее сохранённые значения остаются прежними.

Причина: для метров HTML-поле требовало целый шаг, а общий конвертер округлял
любую дистанцию до целого метра. PostgreSQL-столбцы `plan_distance_km` и
`fact_distance_km` дополнительно ограничивали значение тремя знаками в км.

Контракт: доменный `distanceKm` остаётся числом в километрах; два знака в метрах
требуют пяти знаков в км. UI использует существующее поле и селектор м/км,
без нового состояния, флага или provider-specific ветвления. Yandex API
передаёт тот же контракт, Supabase legacy-схема не меняется. Другие метрики,
калории и формула темпа не меняются.

Миграция `000107` расширяет оба столбца с `numeric(9,3)` до `numeric(11,5)`:
шесть цифр целой части сохраняются, существующие данные не округляются.
Зависимое `ops_readonly.workout_sets` и триггер пересоздаются в той же транзакции;
все имеющиеся SELECT-гранты представления восстанавливаются. Предыдущая
версия API совместима с расширенной точностью, поэтому автоматический down
не сужает столбцы и не теряет новые данные. В production применяется только
штатным Yandex stage workflow перед новой ревизией API; прямой SQL запрещён.
Возможна краткая блокировка `workout_sets` на время DDL, поэтому при
неожиданном объёме/времени применения выпуск останавливается до активации
новой ревизии.

Проверки: `npm run local:verify` (PostgreSQL 17, actor/RLS, план/результат/Live),
`npm run check`, WebKit 390 px, Chromium 430/1440 px. После merge нужны
зелёные CI и production smoke на `fit-training.ru`; миграция в legacy
Supabase и ручное переключение backend не входят в задачу.
