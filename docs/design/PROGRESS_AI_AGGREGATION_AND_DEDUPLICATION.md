# Progress AI — агрегация и дедупликация

Статус: реализовано и полностью проверено локально 11.09.2026. Владельцем
продукта разрешены самостоятельные PR, merge и production rollout с соблюдением
очереди активных PR.

## Результат

Качество клиентского разбора сохраняется, но модель больше не получает сырые
строки подходов и повторяющиеся полные последовательности тренировок. Повторное
обновление без изменения исходных данных возвращает уже сохранённый анализ и не
вызывает модель.

## Полный план

1. На бэкенде собрать компактный JSON по всему выбранному и предыдущему
   периодам. Сохранить точные количества исходных тренировок, упражнений,
   сессий и подходов, чтобы сокращение входа было проверяемым.
2. Для каждого уникального `exercise_ref` сохранить название, тип, мышечную
   группу и источник. Для текущего и предыдущего периода передавать число
   сессий, первую, последнюю и лучшую точку, изменение, вычисленные сигналы и
   уровень уверенности сравнения.
3. Не передавать модели строки отдельных подходов. Для движения с не более чем
   восемью сессиями передавать все агрегированные сессии; для длинной истории —
   максимум восемь контрольных точек, включая начало, конец, равномерные точки
   и лучшие значения. Ни одно уникальное упражнение не удалять из входа.
4. Замеры передавать как число записей, максимум восемь контрольных точек,
   изменение внутри периода и сравнение с предыдущим периодом. Цель сохранять
   полностью. RPE, самочувствие, дискомфорт и комментарии сворачивать по
   одинаковым сигналам; комментарий ограничить 160 символами.
5. Fingerprint строить по полному исходному набору данных, периоду, цели,
   замерам, обратной связи, версии агрегатора, prompt/analysis version и модели.
   Любое значимое изменение инвалидирует кэш; неизменный fingerprint всегда
   использует сохранённый анализ, даже если пользователь нажал «Обновить».
6. Одинаковые одновременные запросы внутри одного экземпляра функции объединять
   в одну активную генерацию. Остальные запросы ждут тот же результат, не
   создавая дополнительных обращений к модели.
7. Обычная генерация — один запрос к модели. Если структурно корректный ответ
   требует исправления, разрешён максимум один дополнительный узкий repair:
   только предыдущий JSON и конкретные нарушения, без повторной отправки всей
   тренировочной истории. Временные сетевые ошибки можно повторять отдельно,
   поскольку ответа модели и расхода токенов при них нет.
8. Сохранить текущий формат UI и чтение старых отчётов. Новая версия анализа
   создаётся только для новых или реально изменившихся данных; при отказе новый
   слабый ответ не сохраняется, старый остаётся доступен.
9. В логах фиксировать только безопасную диагностику: размеры исходного и
   агрегированного контекста, версию агрегатора, сокращённый fingerprint,
   cache hit, совместное ожидание активного запроса и фактические токены ответа.
   Тексты тренировок и анализа в логи не писать.
10. Все автоматические проверки выполнять только с внедрёнными mock-ответами.
    В тестовом окружении прямой сетевой вызов модели блокировать кодом. Обычные
    unit, integration, browser и deployment smoke не расходуют токены. Платный
    AI smoke не запускать автоматически.
11. Выпустить одним PR. Перед merge пропустить более ранний активный PR, затем
    обновиться от `main`, повторить полный `npm run check`, смержить и проверить
    production deployment. После выкладки выполнить один осознанный реальный
    контроль нового анализа и повторное обновление: первое может расходовать
    токены, второе обязано быть cache hit с нулевым расходом модели.

## Ожидаемое потребление

- Новый анализ: ориентир 9–16 тыс. символов агрегированного JSON вместо
  наблюдавшихся 44,5 тыс.; вход модели сокращается примерно на 65–80%.
- Repair: предыдущий готовый JSON и список нарушений вместо повторной полной
  истории; дополнительный вход обычно сокращается на 85–95%.
- Повторное обновление без новых данных: 100% экономии токенов модели.
- С учётом наблюдавшихся повторных обновлений ожидаемое суммарное снижение —
  примерно 80–95%. Точная цифра фиксируется по production usage после выпуска.

## Критерии приёмки

- Все уникальные упражнения текущего и предыдущего периодов представлены.
- Модель не получает массивы сырых подходов.
- Цель, замеры, субъективные сигналы, первый/последний/лучший результат и
  динамика упражнений сохраняются.
- Неизменное ручное обновление не вызывает модель.
- На один содержательный запрос приходится один основной вызов и максимум один
  короткий repair.
- Автотесты физически не могут вызвать live AI.
- Supabase-compatible и Yandex runtime используют одинаковый агрегатор,
  контракт и правила качества.
