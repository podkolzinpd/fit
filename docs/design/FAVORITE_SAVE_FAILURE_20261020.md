2. **Показать диагностику в окне избранного.** Уже существующий механизм запроса сохраняет технические сведения, но это окно выводит только текст ошибки. Подключить готовый компонент с кодом обращения и копированием диагностики. Для серверного поиска переиспользовать подготовленную диагностику из #1729, без второго параллельного механизма. Названия тренировок, аккаунты и токены в журналы не отправлять.

3. **Исправить подтверждённую причину.** После воспроизведения внести точечную правку в нужный слой. Не менять SQL, права или структуру упражнений наугад. Ограничение одного тренера и существующую историю не затрагивать.

4. **Сделать ошибки понятными.** Вместо универсального «Yandex Cloud недоступен» различать потерю соединения, истёкшую сессию, некорректные данные и серверный сбой. Для лимита избранного явно писать: максимум 10 тренировок, нужно удалить одну.

5. **Сохранить введённое при неудаче.** Не закрывать окно и не стирать название. Блокировать повторное нажатие, пока запрос выполняется; автоматический повтор сохранения не включать. Закрывать окно и обновлять список избранного только после подтверждённого успеха.

6. **Закрыть пробел в тестах.** Добавить постоянную проверку production-пути API → PostgreSQL: сохранение плана и завершённой тренировки, фактические веса, время и дистанция, частично выполненные упражнения, лимит, права и ошибки. Отдельно проверить окно на мобильной ширине. Старый тест Supabase не использовать как доказательство исправности нового бэкенда.

7. **Выпустить и проверить реальное сохранение.** Пройти обязательные проверки и штатную публикацию. Финальная приёмка — сохранить тренировку на разрешённом тестовом профиле, увидеть её в избранном после перезагрузки и создать из неё новый план. Одного зелёного CI или доступного `/health` недостаточно.
