## Подтверждено

1. Существующий `/assistant`, без отдельного приложения или чата.
2. Первый выпуск доступен только точному аккаунту тестового тренера.
3. Исходные данные — доступная этому тренеру история клиента и квиз в чате.
4. Цель конкретной программы спрашивается явно, даже если в профиле есть цель.
5. Генерация через LLM в Cloud Function, упражнения только из существующего каталога.
6. Горизонт — ровно четыре недели, 1–3 занятия в неделю по ответу клиента: 4/8/12 назначений.
7. Приоритет — согласованность и пригодность программы.

## Открытые продуктовые решения

Вопросы отправлены пользователю. До ответа это предложения, не утверждённые требования:

- Предлагается черновик → правки → явное добавление в расписание.
- Предлагается первая область: сила/гипертрофия. Частота 1–3 уже подтверждена.
- Поведение при боли/травме: остановка с предметным уточнением или адаптация с
  обязательной проверкой тренером. Боль в старой записи сама по себе не доказывает
  текущую травму; отсутствие обратной связи не означает отсутствие боли.
- Назначение килограммов: предлагается в первой версии не экстраполировать
  исторический максимум; показывать подтверждённый прошлый результат отдельно,
  а план задавать через повторы и субъективную интенсивность.

## Схема

`Assistant → устойчивый ProgramBrief → actor-scoped snapshot → private Cloud
Function → LLM candidate → validator → draft → validated edit → atomic save`.

### Оркестратор

Существующая `fit-assistant-orchestrator` остаётся входом чата. Код разрешает
инструменты и переходы; LLM понимает свободную речь и возвращает ограниченную
поправку анкеты. Модель не выбирает произвольный SQL, адрес сервиса или identity.
Генератор — отдельный инструмент `generate_program` и отдельная Cloud Function.

Server state хранится в текущих conversation/messages/actions. Нельзя полагаться
на последние 20 сообщений как на единственную память: последнее состояние
должно содержать всю накопленную анкету, её версию и выбранного клиента.

Состояния: выбор клиента → цель → уточнение анкеты → подтверждение брифа →
генерация → черновик → сохранено; отдельно отмена и восстанавливаемая ошибка.
Свободная речь может заполнить несколько полей. Уже известные ответы не
переспрашиваются, новые противоречия явно уточняются. Смена клиента сбрасывает
старые ответы и снимок; общая цель профиля не подменяет цель этой программы.

### Контекст клиента

Первое получение истории — после однозначного выбора клиента, до генерации.
Предлагаемое окно — последние восемь недель, с явным временем среза и пробелами.
Два storage adapter используют один чистый агрегатор: Supabase RLS и Yandex
actor transaction. Не переключать отдельный запрос между backend при ошибке.

Из БД: возраст и профильная цель; текущая структурированная цель/этап; завершённые
тренировки, только подтверждённые подходы, регулярность по неделям; прошлые
значения в связке упражнение/дата/подходы/повторы/вес; session RPE, wellbeing,
дискомфорт; последние замеры и их даты. Приватные заметки тренера, личный чат,
вложения, контакты и имя в LLM-контекст не включаются.

Агрегатор считает факты кодом. Плановые значения не заменяют пропущенный факт.
Нет истории — явный `no_completed_workouts`; нет feedback — `unknown`, а не
«всё хорошо». Старые значения не считаются актуальными автоматически. Нельзя
выдать ограниченную выборку за полную: превышение лимита строк — отдельный отказ.

Сохраняются snapshot/version/fingerprint. Перед генерацией и сохранением
проверяются актуальные права. Перед сохранением изменившийся источник требует
явного обновления черновика, а не незаметной подмены данных.

### Квиз

Цель на эти четыре недели и приоритет; опыт и текущая форма/перерыв; дни и время
одного занятия; дата начала; доступное оборудование; актуальные ограничения;
предпочтения и исключённые упражнения; другая физическая нагрузка.
Известные сведения предлагаются для подтверждения, отсутствующие уточняются.

### Генератор

Получает server-validated brief, минимизированный snapshot, версию методики и
актуальный разрешённый каталог. Вызов — от service account; browser не может
подсунуть свой snapshot или обойти разрешение на пилот.

LLM сначала предлагает основу недели: распределение движений, упражнения,
подходы, повторы, отдых и целевую интенсивность, с причинами выбора. Затем
предлагает ограниченное изменение на каждую из четырёх недель. Код разворачивает
шаблон в точные даты. Это один контракт, без четырёх независимых импровизаций.
Разгрузочная неделя не навязывается всем автоматически только из-за длины блока.

Возвращается schema-constrained JSON. Модель выбирает `exerciseRef`; название,
тип и оборудование подставляются сервером из каталога. Custom-упражнения
разрешаются только при достаточной методической разметке. Новая LLM-классификация
упражнения не становится основанием жёсткой проверки без верификации.

### Проверка согласованности

Жёсткие проверки: схема; identity; четыре недели; выбранные дни/оборудование;
существующие активные упражнения; типы нагрузки; исключения; реалистичная оценка
длительности; допустимые объём/интенсивность/изменение между неделями; переход
воскресенье → понедельник. Числовые пороги требуют версии методики и обоснования.

Мягкие критерии: соответствие цели; связь с подтверждённым опытом; баланс
движений; сохранение упражнений для сравнения; объяснимость изменений. Они
оцениваются отдельно от валидности JSON. LLM-критик может дать сигнал, но не
является единственным разрешением на выпуск.

Невалидная программа не показывается как готовая. Не вводить скрытые циклы
платных исправлений. По умолчанию одна генерация на подтверждённый brief;
повтор — явное действие, с серверными лимитами и блокировкой параллельных calls.
Ключ включает actor/client, brief revision, source fingerprint, каталог, правила
и модель. Таймаут после сохранения не создаёт повторные назначения.

### UI и сохранение

Референс — текущие ProgramBriefCard/ProgramDraftCard в AssistantHistoryPage.
Переиспользовать `assistant-flow-card`, choice chips, composer, Field/SaveStatus,
общие error/retry и neutral surface/primary tokens. Primary в квизе — ответ или
подтверждение брифа; в готовом черновике — «Добавить в расписание».

В первой итерации правка в чате меняет условия анкеты. После явного подтверждения
создаётся новый полный черновик; точечная правка отдельных назначений пока не реализована. RPE и отдых сохраняются в существующие поля плана, не только
в пояснение. Все занятия создаются одной транзакцией со стабильными request IDs.

Текущий legacy лимит — четыре workouts в API validator и обоих action RPC.
Для подтверждённой области 1–3 занятия нужны 4–12 workouts. Менять обе схемы миграциями и
проверить rollback/идемпотентность/cross-tenant доступ. Старую историю читать.

### Пилот и наблюдаемость

`VITE_ASSISTANT_PROGRAM_ENABLED` и собственный `VITE_ASSISTANT_PROGRAM_PILOT_USER_IDS`
плюс серверные `ASSISTANT_PROGRAM_ENABLED`/`ASSISTANT_PROGRAM_PILOT_USER_IDS`.
Все флаги default-off, пустой allowlist запрещает всем. Email нужен только для
однократного точного резолва профиля, runtime доступ проверяется по auth UUID.
Вызовы квиза/генератора и сохранение тоже защищены сервером. Уже сохранённые
назначения не удаляются при выключении пилота.

Логи: request ID, release, версия правил/модели, latency, usage, коды проверок.
Не писать сырой brief, медицинские сведения, имена, токены или сообщения клиента.

## Приёмка

1. test@test.com проходит весь чат-сценарий до четырёх недель в расписании.
2. Другой trainer/client, подмена owner/client и прямой вызов не включают функцию.
3. Анкета переживает refresh/повтор, не теряет ответы и не переносится другому клиенту.
4. План/факт/нет данных/устаревший feedback различаются; источники совпадают в обоих backend.
5. Кандидаты с неизвестным ref, неправильными датами, нагрузкой, длительностью
   и нарушением исключений блокируются; правка проходит тот же validator.
6. Сохранение 4/8/12 занятий атомарно, retry после timeout не создаёт дубль.
7. Реальный `/assistant`: 390/430 и 1440, light/dark, длинные тексты,
   loading/empty/error/retry/ready/saved, keyboard и overflow.
8. Локальные API/UI тесты, DB-тесты в CI (пользователь исключил Podman), общий check, зелёный CI, штатный merge, проверка
   Cloud Function и реальное прохождение сценария тестовым тренером.
9. Сравнение с образцовыми программами/benchmark перенесено пользователем на этап
   доработок (2026-09-15); оно не блокирует пилот. Проверки согласованности и
   предметные тестовые сценарии обязательны. Превосходство над базовой моделью не заявляется.

## Предложение по методической разметке каталога

Дополнительная версионированная запись по существующему `exerciseRef`; новые
упражнения и альтернативные идентификаторы не создаются. Два слоя:

1. Факты канонического каталога: ref, активность, точное название, input kind,
   мышцы и оборудование. Требования к комплекту оборудования уточняются: одной
   строки «штанга» недостаточно, если нужны ещё скамья и стойки.
2. Разметка для программирования: семейство движения (присед/выпад, наклон в
   тазобедренном, горизонтальные и вертикальные жим/тяга, изоляция, кор),
   поддержан ли корпус, технические требования, допустимые варианты замены.
   Это описание движения, не медицинская оценка безопасности.

Стартовать с небольшого достаточного набора базовых движений. Перед включением
каждого ref проверить точный вариант, технику и оборудование по существующему
описанию/медиа. Автотесты проверяют актуальность ref, отсутствие retired и дублей,
полноту metadata, совместимые типы нагрузки и покрытие вариантов оборудования.
LLM-классификация может подготовить черновик, но не попадает прямо в production.
Не размеченные custom/редкие движения доступны в обычном каталоге, но не входят
в пул автогенерации. Если тренер требует именно такое упражнение, квиз сообщает
о неподдержанном варианте, а не молча заменяет его.

Validator агрегирует объём по основным движениям и отдельно показывает
вторичное участие. Не складывать условные дробные подходы как измеренный факт.
Сочетание нескольких движений с удержанием корпуса в наклоне — сигнал для
пересмотра, не заявление о неизбежной травме. Ограничения количества/интенсивности
версируются в методике. Покрытие каталога измеряется отдельно от качества программ.

При одном занятии — самостоятельный недельный план с реалистичным объёмом и
полным покрытием основных движений в пределах цели/времени; не сжимать три
занятия в одно. Расписание 2/3 дней учитывает распределение и переход между
неделями. Конкретные схемы зависят от опыта, цели и доступного времени.

## Реализация и оставшаяся проверка

Реализованы агрегатор, actor-scoped Supabase loader, квиз с доказательствами из
последнего сообщения, private CF, проверка программы, календарь 4/8/12,
карточка и атомарное сохранение. Нативный Yandex chat оставлен default-off;
его save RPC обновлён совместимо. Паритет загрузчика с ним пока не заявляется.

Пилотный аккаунт точечно проверен: test@test.com, trainer,
`cbac997f-7641-4251-9ecb-fee777ef1ddc`. Ограничение ровно на один UUID.

Проверки API/unit выполнены. DB integration, финальный CI, выпуск и live
прохождение в production должны быть отмечены после фактического завершения.
Podman и локальная БД исключены пользователем; DB integration выполняется CI.
Утверждения о превосходстве над базовым YandexGPT отсутствуют.
