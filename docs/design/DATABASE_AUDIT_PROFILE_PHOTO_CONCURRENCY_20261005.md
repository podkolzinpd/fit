# Защита первых фотографий профиля от одновременной записи

Первый шаг аудита БД сохраняет фотографии тренера, когда несколько запросов
одновременно создают ещё отсутствующий профиль. Публичный API, интерфейс,
начальная версия профиля и лимит трёх фотографий остаются прежними.

## Границы первого шага

Поток data-media, базовый main `33252066`. Изменяются только серверные
`saveDraft` и `uploadPhoto`, их PostgreSQL-тесты и документация. Миграций,
новых прав, Supabase-изменений и вызовов настоящего Object Storage нет.
Согласованное чтение тренировок и загрузка истории остаются следующими задачами.

## Приёмка

1. Две одновременные первые загрузки сохраняют обе фотографии.
2. Сохранение первого черновика одновременно с загрузкой не удаляет фотографию.
3. Из четырёх одновременных первых загрузок успешны три; четвёртая получает
   `limit_reached`, и удаляются только два её временных объекта.
4. Ошибка записи метаданных откатывает создание профиля и удаляет файлы запроса.
5. Первый сохранённый профиль получает версию 1; переданные клиентом ссылки
   на фотографии не становятся доверенными метаданными.

## Причина и исправление

`SELECT FOR UPDATE` не блокирует отсутствующую строку. Прежний upsert заменял
список фото снимком, построенным до ожидания другого создателя.

Существующая строка по-прежнему блокируется. При её отсутствии сервер выполняет
`INSERT ON CONFLICT DO NOTHING RETURNING`; проигравший создатель перечитывает
строку под блокировкой отдельным запросом. Поэтому список строится из актуальных
серверных метаданных. Первый upload обновляет созданную им строку без лишнего
повышения версии. Запись файлов и подписание URL остаются вне DB-транзакции.

## Доказательства проверки

На отдельном локальном PostgreSQL 17 через Podman первые три теста воспроизвели
потерю фото, стирание фото черновиком и четыре успешных загрузки на старом коде.
На исправленном коде все пять сценариев и полный actor/RLS-набор 76/76 прошли.
Барьер в тестовом connection adapter останавливает оба чтения отсутствующей
строки; SQL выполняется настоящим PostgreSQL. Таймеров и sleeps нет, storage
заменён mock. Очистка касается только синтетического аккаунта этих тестов.

API lint/typecheck, девять trainer-profile unit tests и полный `npm run check`
прошли. Два существующих WebKit-сценария сохранения и загрузки фото прошли
с теми же локальными Yandex test flags, что CI. Первый запуск был skipped без
pilot harness; второй показал legacy login из-за отсутствующих test flags.
Это ошибки настройки проверки, не доказанные регрессии продукта.

`npm run local:verify` остановился на прежней Supabase-цепочке: отсутствует
историческая миграция `20260919145000_source_cutover_migration_window.sql`.
Базу не сбрасывали и историю не исправляли. Независимая чистая Yandex-цепочка
и все её actor/RLS tests проверены успешно.

CI остаётся гейтом передачи PR; более ранний активный PR #1433 выпускается
первым. Production не изменялся, реальный вход или пользовательское фото не
проверялись. UI/native bundle не меняются, новая мобильная сборка не требуется.
