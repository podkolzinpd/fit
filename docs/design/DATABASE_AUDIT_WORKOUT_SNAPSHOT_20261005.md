# Согласованное чтение тренировок

Второй шаг аудита БД защищает ответ `/v1/training-data` от смешивания корня
тренировки, упражнений и подходов из разных сохранений. Клиент и тренер
получают целиком прежний или целиком новый снимок внутри одного запроса.

## Границы задачи

Поток data-media, базовый main `3a0bcf3f`, первый шаг #1434 уже слит и его
API deployment успешно завершён. Общий контракт `PilotTrainingDataResponse`
и frontend repositories не меняются. Изменяется только режим серверной
транзакции `DatabasePilotTrainingDataReader` и его тесты.

Миграций, новых grants, Supabase adapters, UI-изменений и feature flags нет.
История между разными страницами не получает общего снимка: server-side
пагинация и отказ от полной загрузки истории остаются отдельным третьим шагом.
Не подключать локальные проверки к production и не менять данные пользователей.

## Критерии приёмки

1. Сохранение между чтением корня и упражнений не смешивает версии.
2. Сохранение между чтением упражнений и подходов не теряет старые подходы.
3. Следующий запрос видит полностью сохранённую новую тренировку.
4. Оба session-контракта работают; RLS не раскрывает назначения другого тренера.
5. Недействительная сессия и ошибка чтения возвращают ошибку, не частичный ответ;
   транзакция откатывается, соединение освобождается.
6. Snapshot-режим выбирается до разрешения actor и первого SELECT. Остальные
   операции сохраняют прежний режим; actor и настройки не остаются в пуле.

## Причина и решение

READ COMMITTED создаёт новый MVCC-снимок для каждого SQL statement даже внутри
одной транзакции. Между последовательными SELECT сохранение заменяет детей
тренировки: сервер может вернуть старую `version` с новыми упражнениями либо
старые упражнения без подходов.

Для чтения training-data используется `BEGIN ISOLATION LEVEL REPEATABLE READ
READ ONLY` до проверки session и установки actor. Все SELECT одной транзакции
видят один снимок; SQL не ставит write-lock и не требует повторного сохранения.
Существующие transaction helpers получили один явный opt-in режим; issuance
сессий и все mutation продолжают использовать обычный `BEGIN`.

Транзакция охватывает только DB-чтение и сборку DTO, без внешних запросов.
После её начала конкурентное изменение, включая отзыв доступа, становится
видно следующему запросу, не меняя уже начатый снимок. Это не межстраничная
консистентность и не новая гарантия сохранения форм.

## Проверка

Четыре теста с реальным PostgreSQL и fit_api воспроизвели дефект на старом коде:
две границы чтения для read-only и read-write sessions. Connection adapter
дожидается настоящего commit `savePlannedWorkout` между SELECT, без sleep.
После исправления все четыре прошли и проверили повторное чтение, RLS и
отсутствие actor/isolation state в переиспользованном соединении.

Семь unit-тестов проверяют BEGIN до session resolution, оба типа sessions,
отказ невалидной сессии, rollback/release при ошибке и неизменность default mode.
Чистая цепочка Yandex migrations и полный actor/RLS80/80 прошли на отдельном
Podman PostgreSQL17. Полный `npm run check` прошёл: frontend2371/API1070,
DB80 штатно skipped в общем unit-run и отдельно выполнены выше. API lint/types
прошли; два существующих WebKit-сценария training-data error/retry зелёные.
`local:verify` не повторялся: прежний legacy Supabase blocker первого шага
не исправлялся; новая схема не добавляется. CI остаётся гейтом PR.
UI не меняется; прежние loading/empty/error/retry и native bundle сохраняются.
