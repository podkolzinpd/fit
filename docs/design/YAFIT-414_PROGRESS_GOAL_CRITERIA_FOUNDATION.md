# YAFIT-414 — Progress 1.1: основа критериев цели

## Пользовательский результат

Цель остаётся свободным текстом, но рядом с ней можно вручную и без LLM
подтвердить один измеримый критерий. Progress больше не делает вид, что умеет
автоматически оценить старую или произвольную цель: он явно различает
`не настроено`, `нужны данные` и `настроено`.

## Scope 1.1

- Production Supabase и текущий Yandex stage получают одинаковую дочернюю
  сущность `goal_criteria`.
- Схема поддерживает несколько строк на цель для будущего 1.3, но UI 1.1
  редактирует только один критерий.
- В 1.1 доступны уже существующие стандартные источники замеров: вес, талия,
  грудь и бёдра. Их численная оценка, динамика и freshness остаются в 1.2;
  1.1 проверяет только наличие хотя бы одного значения выбранного показателя.
- Operations фиксируются в общем контракте: `decrease_to`, `increase_to`,
  `maintain_range`, `change_by`, `track_only`. Для `change_by` знак величины
  задаёт направление: отрицательное значение означает уменьшение, положительное
  — увеличение; ноль невалиден.
- Ручное сохранение создаёт `confirmed` criterion. Будущий LLM-ответ сможет
  создать только `suggested`; автоматической активации в 1.1 нет.
- Изменение текста цели без одновременного подтверждения критерия переводит
  существующий criterion в `needs_review`.
- Изменение текста и явное подтверждение criterion в одном сохранении выполняются
  атомарно и не создают промежуточного конфликта версий.
- Старые цели возвращаются с `criteria: []`; миграция не создаёт и не угадывает
  критерии.

## Данные критерия

- связь: goal, client partition и owner;
- metric: `weight`, `waist`, `chest`, `hips`;
- operation;
- target value или range;
- unit (`кг`/`см`);
- confirmation status: `suggested`, `confirmed`, `needs_review`;
- optimistic version и position.

## Атомарность и совместимость

`save_client_goal` принимает необязательное поле `criterion`:

- поле отсутствует — старый API-клиент продолжает работать;
- `criterion: null` — цель сохраняется без автоматической оценки;
- object — цель и один criterion валидируются и сохраняются одной транзакцией.

На изменении title старый клиент не теряет criterion, но он становится
`needs_review`. Архивация цели сохраняет историю, cascade применяется только
при реальном удалении цели, которого продуктовый API не выполняет.

## UI 1.1

- Trainer `/clients/:clientId/goal` и Client `/me/goal` используют одну форму.
- Основная цель формы — сохранить цель; criterion является явно необязательным
  разделом `Как оценивать цель`.
- Ручная настройка содержит metric, operation и условные numeric fields.
- Можно удалить criterion и сохранить цель без оценки.
- Progress показывает title, criterion, operation, target/range, status и CTA.
- Статус всегда написан текстом; semantic color не является единственным
  сигналом.

## Намеренно вне scope

- LLM parsing и explanation;
- численная оценка положения относительно цели;
- period dynamics, baseline, freshness/staleness;
- exercise, cardio, regularity и custom metrics;
- несколько одновременно редактируемых criteria.

## Acceptance 1.1

- legacy goal без criterion читается и редактируется без потери данных;
- goal можно создать и сохранить без criterion;
- criterion можно вручную создать, изменить, подтвердить и удалить;
- изменение title требует повторного подтверждения сохранённого criterion;
- отсутствие значения выбранной metric даёт `нужны данные` и CTA;
- наличие значения даёт `настроено`, но не выдумывает достижение цели;
- клиент и тренер видят одинаковый criterion contract;
- LLM и глобальные model/provider settings не меняются;
- RLS/cross-tenant, optimistic conflict и invalid payload покрыты тестами.
