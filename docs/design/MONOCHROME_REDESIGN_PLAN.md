# Fit — план перехода на монохромную айдентику

Статус: **Gate 0–6 и общий client pilot visual audit завершены; Foundation UI
Identity v1 подтверждена на реальных экранах. В production preview доставлены
весь клиентский контур, workout lifecycle, Trainer Today, Trainer Clients и
задачи 18–20 Trainer Client Detail, Create/Edit и Client Goal. Задача 21
Trainer Schedule проходит отдельный rollout**.

Целевой контракт: `docs/UI_IDENTITY.md`. План сохраняет правило проекта:
один явно выбранный экран или один самостоятельный foundation-слой — одна
задача, ветка и PR. Для текущей автономной миграции отдельное ручное решение
между экранами не требуется: переход разрешён после зелёных проверок, merge,
deploy и короткого production smoke. После Client Home, Live и Progress
обязателен один общий visual audit до продолжения остальных задач.

## Безопасная стратегия

Редизайн поставляется как обратимая последовательность маленьких изменений.
До финального выпуска текущий интерфейс остаётся основным, а новая айдентика
доступна только в preview-режиме. Это позволяет сравнивать варианты на реальных
экранах и корректировать направление без массовой переделки уже мигрированных
разделов.

Правила перехода:

- один экран или один shared-слой — одна задача, ветка и PR;
- visual PR не меняет маршруты, данные, права, бизнес-логику и тексты продукта;
- старый интерфейс остаётся безопасным default до общей приёмки;
- новая айдентика включается default-off флагом только для allowlist;
- пилот включается поэкранно: незавершённые маршруты остаются в текущем стиле;
- один и тот же DOM и компоненты обслуживают обе темы — параллельную копию
  приложения для редизайна не создаём;
- переход к следующей контрольной точке возможен только после решения
  `принять`, `скорректировать` или `отклонить`;
- любое изменение должно откатываться выключением одного флага или удалением
  одного изолированного PR, без миграции данных и ручного восстановления.

### Два независимых переключателя

Нельзя смешивать выбор темы и готовность новой айдентики:

1. **Appearance:** существующий выбор пользователя `light / dark`.
2. **Identity:** `current / monochrome-preview`, default — `current`.

В проекте уже есть allowlist для прежнего `dark-pilot`. Он не переименовывается
и не используется для нового дизайна: это отдельный фиолетовый эксперимент.
Новая identity управляется server-managed флагом `monochrome_preview` в
`public.user_feature_flags`, привязанным только к authenticated `user_id`.
Отсутствующая строка, `false` и ошибка чтения означают OFF. Frontend получает
значение как `actor.featureFlags.monochromePreview`; email, frontend-env
allowlist и UI-условия по email запрещены. Список мигрированных маршрутов
подключается route-scoped классами и расширяется по одной экранной задаче.

На немигрированном маршруте участник пилота видит текущую айдентику. На
мигрированном — новый стиль в выбранной им светлой или тёмной теме. Такое
временное различие допустимо только внутри пилота; в общий выпуск выходит
полностью согласованный набор экранов.

## Как показывать каждое изменение

Перед правкой экрана фиксируется одинаковый review-набор. После правки он
повторяется на тех же данных и в том же viewport — тогда сравнение показывает
именно дизайн, а не случайную разницу контента.

| Артефакт | Что должно быть в приёмке |
| --- | --- |
| Scope | точный маршрут, роль пользователя и один изменяемый экран |
| Before | текущий экран на реальных fixture-данных |
| After Light | новый экран в светлой теме, mobile 390 и 430 px |
| After Dark | тот же экран и состояние в тёмной теме |
| Desktop | для тренерского workspace дополнительно 1440×1000 |
| States | все применимые реальные состояния экрана, подтверждённые текущей продуктовой логикой |
| Interaction | focus, клавиатура, scroll, fixed bars, dialog/sheet и safe area |
| Инварианты | что намеренно не менялось: данные, порядок действий, тексты, маршруты |
| Решения | список визуальных вопросов, по которым нужна оценка |
| Итог | `принять`, `скорректировать` или `отклонить` |

Для длинного экрана добавляется один full-page кадр и 2–4 крупные области,
где хорошо видны типографика, CTA, карточки и данные. Ревью нельзя строить на
единственном «красивом» happy path. При этом нельзя создавать искусственные
`loading`, `empty`, `error`, `success` или другие состояния только ради
чек-листа: проверяются все и только те состояния, которые существуют в реальной
продуктовой логике выбранного экрана.

### Definition of Ready

Задача готова к началу, если:

- указан реальный маршрут и владелец роли;
- зафиксированы before-кадры и fixture/data state;
- определено единственное primary-действие;
- перечислены состояния и соседние сценарии, которые нельзя затрагивать;
- понятно, как отдельно включить preview и как его выключить.

### Definition of Done

Задача завершена, если:

- доступны сравнимые before/after для обеих тем;
- проверены предусмотренные состояния, размеры и интеракции;
- продуктовая логика и data contract не изменились;
- автоматические проверки и visual screenshots проходят;
- выключение preview возвращает прежний интерфейс;
- по контрольной точке принято явное решение.

Если решение — `скорректировать`, задача остаётся открытой: исправления
показываются на том же наборе кадров. Если `отклонить`, PR не входит в
следующий этап, а preview остаётся на предыдущей принятой версии.

## Контрольные точки

### Gate 0 — контракт и baseline

Выполнить задачу 1: собрать реальные экраны, literal-цвета, состояния и
эталонные screenshots. Визуальных изменений нет. Проверить полноту списка и
подтвердить Client Home как первый пилот.

### Gate 1 — foundation вне продуктовых экранов

Выполнить задачи 2–7 в изолированном component preview: типографическую шкалу,
палитры, actions/forms, surfaces/states, shell, navigation и icons в
светлой/тёмной теме. До финальной приёмки foundation не менять feature CSS.

Gate 1 выполняется последовательно: задача 2 проверяет только Onest и компактную
типографику в изолированном monochrome preview. Палитра начинается с задачи 3
и не должна попадать в типографический PR. До приёмки первого Gate, который
меняет реальный интерфейс, обязателен восстановленный runtime и фактическая
Playwright before/after сверка.

Проверяем:

- достаточно ли тёплый `#242426` и не выглядит ли он просто чёрным;
- не уходит ли `#F1EDE6` в жёлтый на тёмном фоне `#111214`;
- действительно ли 14 px подходит основному контенту;
- сохраняется ли визуальная иерархия Onest без тяжёлого 800.

### Gate 2 — финальная приёмка foundation

После задачи 7 остановиться и принять foundation-блок целиком: typography,
palettes, actions/forms, surfaces/states, semantic colors, shell, navigation и
icons. Gate 2 не содержит отдельной implementation-задачи. До явного решения
по этой контрольной точке нельзя начинать Client Home или другой продуктовый
экран.

### Gate 3 — Client Home

Выполнить только задачу 8 и открыть её в route-scoped preview. Это первый
реальный продуктовый экран. Показать обе темы, все состояния и отдельный
before/after. В текущей автономной сессии переход к Live разрешён после зелёных
проверок, отдельного merge/deploy и фиксации результата Client Home.

После Client Home проводится первая продуктовая дизайн-проверка. Она оценивает
не только соответствие утверждённой палитре, но всю новую визуальную айдентику:

- Onest и типографическую иерархию;
- spacing и плотность;
- радиусы и геометрию;
- поверхности и карточки;
- primary, secondary и ghost actions;
- navigation;
- inputs и controls;
- иконографику;
- все применимые реальные состояния компонентов;
- light и dark;
- отсутствие наследия coral и purple;
- отсутствие локальных ad-hoc цветов и стилей.

Экран должен восприниматься как новый визуальный язык Fit даже в grayscale.
Если результат выглядит как существующий интерфейс, который только перекрасили
и перевели на Onest, пилот не принимается.

После принятия Client Home использованные foundation-паттерны фиксируются в
`docs/UI_IDENTITY.md` как **UI Identity v1**. С этого момента они становятся
базой для следующих экранов и меняются только как осознанная глобальная
корректировка с повторной проверкой уже принятого Home.

### Gate 4 — Live-тренировка

После принятого Home выполнить задачу 15. На ней проверить повторяемое primary,
крупное число, таймер, confirmed/upcoming состояния, нижнюю фиксированную панель
и использование янтарного только как сигнала текущей работы.

Live может расширить UI Identity v1 специфическими паттернами тренировки, но не
должен без необходимости создавать альтернативные версии уже утверждённых
кнопок, полей, карточек, навигации и других базовых компонентов.

### Gate 5 — Progress

После принятого Live выполнить задачу 10. На ней проверить плотность данных,
графики, легенды, neutral/semantic series и отсутствие лишнего dashboard-вида.

Progress может расширить UI Identity v1 паттернами данных и графиков. Новые
варианты базовых компонентов допустимы только тогда, когда утверждённый паттерн
не решает реальную продуктовую задачу; причина и новый контракт отдельно
фиксируются в приёмке и в `docs/UI_IDENTITY.md`.

### Gate 6 — остальной клиентский контур

Последовательно выполнить задачи 9, 11–14. Каждый экран принимается отдельно;
после блока проводится сквозной client-flow smoke в обеих темах.

### Gate 7 — тренерский контур

Последовательно выполнить задачи 16–24. Сначала Today, список и карточку
клиента, затем формы, цель, расписание, прогресс, каталог и профиль. Для каждого
workspace обязательна desktop-проверка 1440×1000, для применимых экранов —
mobile 390/430.

### Gate 8 — auth и ассистент

Выполнить задачи 25–26 отдельными PR. Auth проверяется без изменения OAuth и
callback-логики; ассистент — без изменения orchestration, matching и fallback.

### Gate 9 — выпуск

Выполнить задачи 27–28: общий accessibility-аудит, visual regression,
WebKit/iOS safe areas и production smoke. Только после общей приёмки сделать
`monochrome` основной identity. Rollback-флаг сохраняется минимум на один
релизный цикл.

Контрольные точки не увеличивают оценку в 28 implementation-задач: это
обязательные паузы на просмотр между ними. Если на Gate 3–5 меняется глобальный
токен или типографическая роль, добавляется одна stabilization-задача на
повторную проверку уже принятых экранов.

## Протокол корректировок

Корректировка сначала классифицируется:

- **глобальная** — палитра, шрифт, размерная роль, радиус, тип кнопки;
- **компонентная** — один shared-компонент во всех местах;
- **локальная** — композиция или состояние одного экрана.

Глобальное решение сначала обновляет `docs/UI_IDENTITY.md`, затем shared-токены
и все уже принятые screenshots. Компонентное решение не исправляется локальным
CSS на одном экране. Локальная правка не должна попутно менять соседние
маршруты. После любой корректировки повторяется тот же review-набор — иначе
невозможно понять, исправлена ли исходная проблема.

## Лестница выпуска и откат

1. **Local component preview:** только design specimens, без product routes.
2. **Local route preview:** один мигрированный экран на fixture-данных.
3. **Staging allowlist:** владелец продукта видит принятые экраны на реальных
   сценариях, остальные пользователи — текущий UI.
4. **Закрытый pilot:** небольшой фиксированный allowlist после Gate 5.
5. **Полный preview:** вся команда после окончания экранной миграции.
6. **Default-on:** только после Gate 9 и production smoke.
7. **Удаление fallback:** не раньше одного стабильного релизного цикла после
   default-on.

При критической визуальной или функциональной регрессии сначала выключается
identity-флаг. Откат не должен требовать revert нескольких PR или изменения
пользовательских данных. Старые visual baselines хранятся до завершения
релизного цикла.

## Оценка

Рекомендуемый объём — **28 задач**:

- 7 foundation и shared-задач;
- 5 клиентских экранов;
- 3 задачи жизненного цикла тренировки;
- 9 тренерских и служебных экранов;
- 1 задача auth-flow;
- 1 задача ассистента;
- 2 финальные задачи качества и выпуска.

Если разделять каждый маршрут и каждую форму в отдельный PR, объём вырастет до
30–32 задач. Оценка 28 предполагает объединение только тех состояний и
подмаршрутов, которые уже используют один feature-компонент и один контракт.

## 1. Foundation и shared — 7 задач

1. **Инвентаризация визуальных токенов и baseline.** Найти literal-цвета,
   пересекающиеся token groups и список защищённых screenshot states. Никаких
   визуальных изменений в этой задаче. Результат:
   `docs/design/MONOCHROME_GATE_0_BASELINE.md`.
2. **Onest и компактная типографика.** Подключить шрифт, ввести целевые роли,
   сохранить 16 px в редактируемых полях и проверить переносы. Выполняется
   только в `docs/design/preview/monochrome-typography.html`; приложение и его
   глобальные стили в этой задаче не меняются. Результат:
   `docs/design/MONOCHROME_GATE_1_TYPOGRAPHY.md`.
3. **Светлая палитра.** Добавить целевые семантические значения
   `#FBFAF7 / #242426 / #EFEDE8`, не перекрашивая feature CSS напрямую.
   Результат: `docs/design/MONOCHROME_GATE_1_LIGHT_PALETTE.md`.
4. **Тёмная палитра.** Добавить `#111214 / #F1EDE6 / #1D1E21`, убрать
   зависимость от фиолетового glow и проверить паритет токенов. Результат:
   `docs/design/MONOCHROME_GATE_1_DARK_PALETTE.md`.
5. **Действия и формы.** Мигрировать primary/secondary/tertiary/destructive,
   поля, сегменты, switches, focus, pending и disabled. Результат:
   `docs/design/MONOCHROME_GATE_1_ACTIONS_FORMS.md`.
6. **Поверхности и состояния.** Мигрировать cards, sheets, dialogs, menus,
   loading, empty, error/retry, success и SaveStatus. Результат:
   `docs/design/MONOCHROME_GATE_1_SURFACES_STATES.md`.
7. **Shell, навигация и иконки.** Обновить phone frame, bottom tabs, page header,
   fixed bars и убрать неоднозначные Unicode-иконки там, где есть Fit SVG.
   Результат: `docs/design/MONOCHROME_GATE_1_SHELL_NAV_ICONS.md`.

## 2. Клиент — 5 задач

8. **Client Home / Кабинет.** Сохранить voice-first порядок, следующую
   тренировку, недельный ритм, highlight и install prompt.
9. **Мои тренировки.** Предстоящие, требующие решения, история и empty state.
10. **Мой прогресс.** Summary, периоды, лучший результат, карта тела, замеры,
    график и история без добавления новых метрик.
11. **Клиентский профиль.** Профиль, подключения тренеров, уведомления и
    обратная связь.
12. **Карточка клиента и редактирование.** `/me`, `/me/edit`, first-run и
    связанные формы при сохранении текущего поведения.

## 3. Жизненный цикл тренировки — 3 задачи

13. **Создание и редактирование тренировки.** Voice/text/catalog, review, plan,
    fact и save states в существующем route flow.
14. **Карточка тренировки, завершение и история упражнения.** План, факт,
    feedback, личный рекорд, частичное выполнение и exercise history.
15. **Live-тренировка.** Текущий подход, confirmed/upcoming work, таймер отдыха,
    изменение структуры и завершение с приоритетом repeated primary action.

## 4. Тренер и служебные экраны — 9 задач

16. **Trainer Today.** Голосовой старт, задачи по клиентам, review и assignment.
17. **Список клиентов.** Поиск, статусы, empty/error и плотное сканирование.
18. **Карточка клиента.** Контекст, действия, тренировки, цель и прогресс без
    превращения экрана в dashboard grid.
19. **Создание и редактирование клиента.** Формы, validation и destructive
    flows без изменения data contract.
20. **Цель клиента.** Просмотр, этапы, редактирование, empty/error и сроки.
21. **Расписание.** Mobile compact shell и 1440×1000 с прежней информационной
    архитектурой.
22. **Trainer Progress и замеры.** Summary, периоды, графики, формы замеров и
    связанные состояния.
23. **Каталог упражнений.** Поиск, media, empty/error и detail-переходы.
24. **Профиль тренера.** Настройки, уведомления, подключения и обратная связь.

## 5. Auth-flow — 1 задача

25. **Вход, подключение и восстановление доступа.** Auth, Join, Forgot/Reset и
    callback-состояния как одна визуальная семья без изменения OAuth-логики.

## 6. Ассистент — 1 задача

26. **Ассистент.** История, composer, распознавание, ambiguity, draft/result и
    сохранение. UI-редизайн не меняет LLM orchestration, matching или fallback.

## 7. Качество и выпуск — 2 задачи

27. **Полный паритет тем и доступность.** Контраст, focus-visible, screen reader
    names, reduced motion, 44 px targets, клавиатура и достижимые состояния.
28. **Visual regression и выпуск.** Обновить согласованные baseline для Client
    390/430 и Trainer 1440, проверить WebKit/iOS safe areas и production smoke.

## Рекомендуемый порядок

1. Пройти Gate 0–2 и не начинать массовую миграцию до стабильных shared
   контрактов.
2. Принять Client Home, Live и Progress по отдельности: на них проверяются
   композиция, repeated primary, данные и обе темы.
3. После трёх принятых пилотов перейти к остальному клиентскому и workout
   lifecycle.
4. Затем мигрировать тренерские экраны, auth и ассистента.
5. Завершить общей accessibility, visual regression и staged rollout.

## Граница каждой задачи

Каждая задача должна содержать:

- точный маршрут и реальные состояния до изменения;
- список переиспользуемых Fit-примитивов и токенов;
- один primary action;
- светлую и тёмную приёмку;
- целевые тесты и visual screenshots;
- список намеренно не затронутых соседних сценариев.

Нельзя объединять весь переход в один PR или менять продуктовую логику под видом
визуальной миграции.
