## Согласованный план — исходная нумерация и формулировки

Сейчас получился замкнутый круг: клиент в архиве, пригласить его нельзя, а кнопка возврата скрылась из-за ошибки.

Правильно сделать так:

1. **В архивной карточке — кнопка «Вернуть из архива».** Она доступна тренеру, у которого есть право восстановить клиента. Кнопки приглашения здесь быть не должно.

2. **После нажатия клиент возвращается в активный список.** Все тренировки, результаты, заметки и связи сохраняются. Новая карточка не создаётся.

3. **Приглашение доступно после восстановления**, если спортсмен ещё не подключил аккаунт. Тренер нажимает «Пригласить клиента» и получает ссылку.

4. **Если аккаунт уже подключён, приглашение не требуется.** Кнопку не показываем. Если клиент подключился прямо во время просмотра карточки — обновляем её состояние вместо непонятного сообщения о недостатке прав.

5. **Если восстановление не удалось**, клиент остаётся в архиве. Показываем понятную ошибку и возможность повторить.

В коде нужно исправить именно условие отображения кнопки восстановления. Сервер уже умеет возвращать клиента из архива — расширять права или переделывать весь процесс не нужно.

Проверить нужно полный путь: **архив → восстановление → активная карточка → создание приглашения**, а также сохранность данных и запрет восстановления без прав.

## Проверка существующего перед кодом

- Уже работает: `set_client_archived`, expectedVersion/права, список архива с действием «Восстановить», share dialog. Новые SQL/API не нужны.

- Меняем: зависимость возврата от скрытого в архиве memberships → `canArchive`; приглашение скрывается в архиве; после отказа приглашения перечитывается актуальная карточка; восстановление получает pending/error/retry и обновление связанных текущих запросов.
- Подтверждено: в SQL migration54 архив исключён из list_accessible_client_trainers, но JSX возврата требует currentMembership.isRoot. Соседнее условие приглашения проверяет только hasAccount=false. Owner canArchive отдельно приходит и для архива.
- Baseline: локальная native-only сборка текущего main, тренер Lime, WebKit390; синтетические API с архивным memberships=[] как в реальной БД. Исходный пользователь подтвердил архив. Реальные аккаунты и приглашения не используются.
- До задачи: изолированная PostgreSQL17 —3/3 existing lifecycle/link/archive tests,6/6 матрица SQL (откатываемые транзакции), WebKit3/3 active/archive/late-link; последний UI baseline уточняется с реальным пустым memberships.
- Не проверено: физический телефон и реальные аккаунты. Видео не объявляется просмотренным; причина установлена по коду/БД/локальному интерфейсу и подтверждению пользователя.
