## 0. Статус реализации

Реализация завершена в feature-ветке и готова к production rollout:

- персональный эксперимент хранится в приватной таблице и приходит во frontend только как булево значение текущей сессии;
- включение берёт глобальную транзакционную блокировку, выключает возможные прежние назначения и требует ровно одну активную запись;
- выключение требует ноль активных записей;
- email не входит во frontend bundle, runtime-конфигурацию или аналитику;
- API-сводка повторяет действующие правила рабочего экрана и суммирует вопросы с непрочитанными чатами;
- визуальная браузерная приёмка на мобильном viewport пройдена после проверки контраста;
- полный `npm run check` пройден: 1 951 frontend-тест, 914 API-тестов, инфраструктурные policy-тесты и production build;
- production deployment и включение единственной записи выполняются после merge в `main` по уже полученному разрешению.

## 1. Цель и границы

Нужно показать новый интерфейс расписания только одному тренеру. Для всех остальных тренеров и клиентов приложение должно остаться визуально и функционально неизменным.

В пилот входят:

- недельный обзор расписания;
- дневной таймлайн;
- плавающая кнопка создания тренировки;
- новая композиция нижней навигации на экране Schedule;
- карточка незавершённых действий с колокольчиком;
- карточка входящих вопросов и сообщений;
- объединённый вход в вопросы тренеру и обычные чаты;
- тёмная графитовая визуальная система с салатовым акцентом.

В пилот не входят:

- изменение бизнес-логики тренировок;
- изменение прав доступа к клиентам, тренировкам и чатам;
- массовый rollout;
- перенос остальных экранов на новый дизайн;
- клиентские фотографии: текущая модель клиента их не содержит, поэтому используем инициалы;
- массовый rollout или включение пилота для любой другой учётной записи.

## 2. Зафиксированные продуктовые правила

### Колокольчик

Показывает количество незавершённых действий, которые сейчас находятся на рабочем экране тренера:

`pendingActionCount = trainerActionItems.length + trainerPlanningItems.length`

Сюда входят:

- неотвеченный вопрос тренеру;
- отмеченный клиентом дискомфорт;
- прошлый план, который ждёт решения;
- отсутствие следующей тренировки, если напоминание не отложено.

Текущая логика гарантирует максимум одну строку на клиента: срочное действие имеет приоритет над напоминанием о планировании.

Нажатие на карточку переводит на `/today#trainer-attention`. Рабочий экран остаётся единственным местом, где выполняются и откладываются эти действия.

### Окно сообщений

Показывает общую входящую коммуникацию:

`inboxCount = unresolvedQuestionCount + unreadChatMessageCount`

Где:

- `unresolvedQuestionCount` — количество строк из `listTrainerAttention()`, у которых заполнен `clientQuestion`;
- `unreadChatMessageCount` — сумма `unreadCount` всех элементов `chat.listThreads()`.

Нажатие открывает `/chat`, где отображаются две секции:

1. `Вопросы тренеру` — имя клиента, превью вопроса и время; переход в `/workouts/:workoutId?reply=1`.
2. `Сообщения` — существующий список диалогов; переход в `/chat/:conversationId`.

Вопрос тренеру намеренно входит в оба счётчика:

- в колокольчик — как незавершённое действие;
- в сообщения — как входящая коммуникация.

Обычное непрочитанное сообщение увеличивает только счётчик сообщений. Оба визуальных счётчика показывают `99+` вместо значений больше 99.

### Состояния загрузки

- во время первой загрузки показываем нейтральный skeleton;
- при ошибке источника показываем `—`, а не ложный `0`;
- если один из источников сообщений недоступен, не складываем частичный результат молча;
- после ответа, закрытия вопроса, чтения сообщения, создания/переноса тренировки или snooze обновляем связанные запросы сразу.

Предпочтительный контракт сессии:

```ts

    trainerScheduleV2: boolean
  }
}
```

Frontend переносит значение в `actor.experiments.trainerScheduleV2`.

Итоговое условие:

```ts
const scheduleV2 = actor?.role === 'trainer'
  && actor.experiments.trainerScheduleV2 === true
```

## 4. Архитектура frontend

### 4.1. Не дублировать бизнес-логику Schedule

Вынести из текущего `SchedulePage` общий model/hook:

```ts
useTrainerScheduleModel()
```

Он отвечает за:

- выбранную дату и query params;
- неделю и двухнедельный период;
- загрузку тренировок;
- группировку и сортировку по дням;
- `timed` и `untimed`;
- переходы неделя → день → неделя;
- предыдущий/следующий период;
- переход к сегодняшней дате;
- автофокус таймлайна.

После этого оставить два presentation-компонента:

- `TrainerScheduleV1` — текущая разметка без визуальных изменений;
- `TrainerScheduleV2` — новая разметка из утверждённого макета.

Оба компонента получают одинаковую модель и используют существующие repository-методы и маршруты.

### 4.2. Общий workspace summary

Не копировать четыре тяжёлых запроса с Today непосредственно в Schedule. На холодном открытии текущий `workouts.list()` может загружать всю историю тренировок страницами по 100 записей.

Добавить лёгкий backend-контракт:

```ts
interface TrainerWorkspaceSummary {
  pendingActionCount: number
  unresolvedQuestionCount: number
  unreadChatMessageCount: number
  inboxCount: number
  updatedAt: string
}
```

Backend рассчитывает его по тем же правилам, которые использует рабочий экран:

- учитывает приоритет `question → discomfort → past_plan`;
- исключает snoozed planning reminders;
- исключает архивных и недоступных клиентов;
- считает только диалоги текущего тренера;
- не возвращает содержимое сообщений в summary.

Frontend использует общий `useTrainerWorkspaceSummary()` на Today, Schedule и в badges. Подробные списки загружаются только после перехода на Today или Chat.

### 4.3. Объединённый inbox

Расширить текущий список `/chat`, не создавать параллельную систему сообщений:

- сверху секция нерешённых вопросов;
- ниже существующие chat threads;
- вопрос и чат визуально различаются;
- вопрос не помечается прочитанным простым открытием списка;
- вопрос исчезает после ответа или явного закрытия;
- сообщения используют существующее поведение read/unread и realtime refresh.

Эта секция показывается только тренеру с `trainerScheduleV2`.

## 5. Поведение Schedule V2

### Недельный режим

- заголовок `Расписание`;
- выбор даты через календарь;
- предыдущая и следующая неделя;
- диапазон дат;
- полоска дней недели;
- выбранный день выделен салатовым;
- карточки дней в две колонки;
- в карточке: день, дата и компактный список тренировок;
- пустой день имеет спокойное состояние без декоративной ошибки;
- сохраняется режим `2 недели`, даже если его нет в референсе;
- FAB создаёт тренировку с выбранной датой.

### Дневной режим

- крупная дата и день недели;
- карточка незавершённых действий;
- карточка вопросов и сообщений;
- часовой таймлайн;
- линия текущего времени только для сегодняшней даты;
- карточки тренировок используют существующие статусы;
- завершённая тренировка получает check;
- тренировки без времени показываются отдельным блоком над таймлайном;
- FAB открывает `/workouts/new?date=:selectedDate`;
- аватар — инициалы клиента, пока в доменной модели нет фото;
- длинные имена и упражнения обрезаются одной строкой без горизонтального scroll.

### Контролы в шапке

Нельзя выпускать декоративную шестерёнку без действия. В пилоте она открывает меню Schedule:

- `Сегодня`;
- `Выбрать дату`;
- `Показать неделю`;
- `Показать 2 недели`.

Если такое значение иконки не проходит продуктовую проверку, заменить её на overflow/calendar до начала разработки.

### Нижняя навигация

Для пилотного Schedule используется композиция из макета:

`Сегодня → Расписание → Клиенты → Ассистент`

Маршруты и доступность Assistant не меняются. Если Assistant недоступен пользователю по действующему флагу, сетка должна корректно перестраиваться без пустого места.

## 9. Тестирование

### Unit/component

- target UUID + role trainer → V2;
- тот же UUID + client role → V1;
- другой trainer UUID → V1;
- отсутствующий/ошибочный experiment → V1;
- pending actions считаются по действующей приоритетной логике;
- snoozed planning не считается;
- inbox = unresolved questions + unread chat messages;
- несколько вопросов одного клиента считаются как несколько входящих вопросов;
- значения больше 99 отображаются как `99+`;
- ошибка источника не превращается в `0`.

### Integration/API

- один тренер не видит assignment другого;
- summary не включает чужих клиентов и диалоги;
- ответ на вопрос уменьшает оба счётчика;
- read chat уменьшает только inbox;
- snooze уменьшает только pending actions;
- перенос/создание/отмена тренировки корректно пересчитывает planning;
- архивный клиент исключён.

### E2E

- вход именно под назначенным тренером;
- неделя → день → неделя;
- 2 недели;
- выбор даты и `Сегодня`;
- FAB и предзаполненная дата;
- переход по колокольчику на очередь;
- переход по сообщениям в объединённый inbox;
- ответ на вопрос и обновление badges;
- чтение чата и обновление inbox;
- rollback флага возвращает V1.

### Visual/accessibility

- 390 и 430 px;
- desktop phone frame 1440 px;
- safe-area iOS;
- light theme не должна случайно применяться внутри V2;
- 0, 1, 9, 99+ для обоих счётчиков;
- длинные имена и названия упражнений;
- tap targets минимум 44 px;
- focus-visible, screen-reader labels и контраст;
- FAB и нижняя панель не перекрывают события.

## 13. Подтверждённый план продуктовой доводки — 25 сентября 2026 года

План зафиксирован после повторной сверки production-скриншотов с двумя
исходными макетами. Исходный scope и порядок пунктов сохранены; изменения не
расширяют эксперимент на другие аккаунты.

1. Оставить один server-side source of truth для двух показателей: колокольчик
   равен рабочей очереди тренера, сообщения равны нерешённым вопросам плюс
   непрочитанным сообщениям. Ошибку источника показывать как `—`, а не как
   ложный ноль.
2. Довести общую рамку: чёрная safe-area на маршрутах пилота, корректные
   отступы, нижняя навигация и FAB без перекрытий. Вне пилотного Schedule V2
   тема и системная область не меняются.
3. В дневном расписании выполнять автопрокрутку один раз при открытии даты,
   оставлять 2–2,5 часа контекста над текущим временем или ближайшей
   тренировкой и не перезаписывать ручную прокрутку. Убирать дублирование
   часовой подписи, если рядом проходит линия текущего времени.
4. В недельном расписании сохранить подписи дней над зелёной полосой,
   статистику периода и двухколоночную сетку. Отменённые занятия не входят в
   количество тренировок и клиентов. Пустая карточка явно говорит
   «Свободный день».
5. Цвет статусов несёт продуктовый смысл: будущий план — акцентный; прошедший
   незавершённый план, пропуск и завершённые состояния — спокойные. Для
   скринридера статус дублируется текстом, чтобы смысл не зависел только от
   цвета.
6. Плюс создаёт тренировку именно на выбранную дату и остаётся визуально выше
   нижней панели и safe-area.
7. Окно входящих объединяет вопросы тренеру и сообщения, сохраняет прямые
   переходы в ответ/чат и даёт явный повтор отдельно для каждого не
