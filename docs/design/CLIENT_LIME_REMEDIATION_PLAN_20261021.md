## PR3. Свайп удаления упражнения и подхода у клиента — новое требование

Переиспользовать WorkoutSwipe, WorkoutGestureList, deleteLiveExercise,
requestRemoveLiveSet и текущие removeExercise/removeSet/атомарные операции
раундов. Существующие места: WorkoutsPages.tsx swipeLive (~3815),
swipeSet (~3934), WorkoutGestureList nativeSwipe (~4437);
реализация — WorkoutGestures.tsx. Сейчас эти подключения ограничены
coachReference. Не включать тренерский флаг и не копировать весь тренерский экран.

Свайп только раскрывает действие «Удалить»; запись происходит после нажатия
и существующего подтверждения. Закрытие/обратный свайп/отмена сохраняют данные.
Жест замены упражнения не добавляется: пользователь запросил удаление,
действующая замена через меню остаётся.

Сохранить правила тренерского свайпа подхода: подтверждённый подход и последний
оставшийся подход одиночного упражнения не удаляются этим жестом;
для групп/раундов — только уже поддержанная атомарная операция и её ограничения.
Существующие пункты клиентского меню не ужесточать и не расширять молча.
Удаление упражнения, включая выполненные данные, проходит через существующее
явное предупреждение; права и серверные команды не изменяются.

Особая приёмка:
- короткий тап по весу/повторам выделяет значение и открывает ввод;
- горизонтальный свайп раскрывает нужную строку, не упражнение-родитель;
- вертикальное движение прокручивает, удержание карточки переносит;
- жест не забирает активное редактируемое поле, заметку, видео или кнопку;
- свайп не подтверждает подход, не снимает галочку и не запускает отдых;
- save/confirm/reorder pending исключают конкурирующее удаление;
- отмена, повторный тап, ошибка/retry и конфликт записи не теряют другие факты;
- удаление текущего упражнения/подхода корректно согласовано с текущей фазой,
  активным упражнением и таймером через существующий путь удаления;
- обе плотности, обе темы, ON/OFF,390/430, WebKit/Chromium,
  клиент без тренера/с тренером; тренерский свайп остаётся рабочим.
Не добавлять новую кнопку-ручку для переноса карточки.

## Порядок публикации

Последовательно: PR0 →1 →2 →3 →4 →5 →6 →7.
Перед кодом каждого — свежая проверка существующего; перед merge —
актуальный main и обязательный зелёный CI, затем публикация в тот же пилот
и проверка реального результата. Снимки и фикстуры дополняют, но не заменяют
проверку публикации. Общий код проверяется у клиента вне пилота и тренера.
Параллельная подготовка независимых частей допустима, публикация не смешивает
несколько непроверенных изменений в один результат.

Не ждём готовности всех семи исправлений: каждый готовый PR выпускается
отдельно. Красный CI не обходим. Более ранние активные PR учитываем по очереди;
уже разрешённый владельцем обход застрявшей ветки фиксируем отдельно,
не сливаем чужую ветку вместо её автора.

После каждой публикации обновлять реестр: ID → commit → снимок/проверка →
остаточное ограничение. «Все проблемы закрыты» возможно только после этой
сверки; физическое устройство и непройденные состояния не помечать проверенными
по зелёному браузерному тесту.
