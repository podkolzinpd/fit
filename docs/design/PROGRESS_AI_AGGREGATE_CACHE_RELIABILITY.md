# Progress AI — надёжный агрегат и кеш без лишних токенов

Статус: утверждено владельцем продукта 14.09.2026. Разрешены самостоятельные
PR, merge и production rollout с соблюдением очереди активных PR.

Связанная задача: [#913](https://github.com/podkolzinpd/fit/issues/913).

## Пользовательский результат

Ручное создание или обновление ИИ-анализа работает для полного доступного
периода. Неизменные данные возвращают готовый анализ без обращения к модели.
Новый запрос всегда получает компактный, но содержательный агрегат и не падает
из-за размера. Автоматические проверки не вызывают live AI и не расходуют
токены модели.

## Неизменяемый план

### 1. Восстановить вызовы кеша и защиты генерации

- Добавить forward-only миграцию, которая подтверждает минимальные
  `SELECT/INSERT/UPDATE` для `service_role` на двух таблицах сводок, `EXECUTE`
  на функциях кеша и generation guard и обновляет schema cache PostgREST.
- Не обращаться к модели, пока проверка кеша и получение generation lease не
  завершились успешно.
- При ошибке писать только безопасную техническую причину: название операции,
  код и короткое сообщение Supabase, без аргументов RPC, тренировок, токенов и
  персональных данных.

### 2. Гарантировать размер агрегированного JSON

- Считать статистику по всем упражнениям текущего и предыдущего периодов.
- Для наиболее значимых движений сохранять подробные контрольные точки.
- Остальные движения передавать компактным индексом и общим rollup, без сырых
  строк подходов.
- Если вход всё ещё велик, сначала сокращать число подробных движений, затем
  низкосигнальную часть индекса; количество свёрнутых движений сохранять в
  coverage.
- Итоговый сериализованный агрегат всегда должен быть не больше целевого
  бюджета 19 000 символов при жёстком серверном пределе 20 000. Пользователю не
  предлагается выбирать меньший период из-за внутреннего размера данных.
- Поднять версию агрегатора, чтобы старый кеш не смешивался с новым контрактом.

### 3. Дедуплицировать по фактическому входу модели

- Fingerprint строить из prompt/analysis/aggregation/model version и итогового
  агрегированного JSON, а не из сырых строк тренировок.
- Повторное ручное обновление при неизменном агрегате возвращает точный кеш и
  расходует `0` токенов.
- Изменение данных, влияющее на модельный агрегат, создаёт новый fingerprint и
  допускает ровно один платный вызов через существующий generation guard.

### 4. Проверить без расхода токенов

- Добавить unit-тесты для обычного месяца и заведомо большого периода, включая
  сотни упражнений, длинные названия и комментарии.
- Проверить жёсткий лимит, наличие подробных сильных сигналов, полный coverage
  через компактный индекс/rollup и стабильность fingerprint.
- Проверить кеш и generation guard на локальной Supabase: права `service_role`,
  cache hit, один lease на параллельные запросы.
- Все provider-вызовы в unit/integration/browser тестах заменить заглушками;
  live AI smoke не запускать локально, в CI и при production-проверке.

### 5. Выпустить последовательно

- Перед merge проверить очередь: пропустить только более ранний активный PR;
  старые неактивные PR не блокируют выпуск.
- После зелёного CI смержить один PR.
- Дождаться успешного применения миграции, затем успешных deployment Supabase
  Function и Yandex Function; при необходимости повторно запустить deployment
  функции уже после базы.
- Production проверять по health, версии и безопасным логам. Платный контрольный
  запрос не запускать: первый содержательный анализ пользователь проверит
  самостоятельно на production.

## Acceptance matrix

| Пункт | Результат | Проверка | Статус |
| --- | --- | --- | --- |
| 1 | RPC кеша и guard доступны production-функции | локальные SQL-тесты + production logs | Локально подтверждено: 91 файл, 1264 SQL-теста |
| 2 | Любой агрегат укладывается в 19 000 символов | unit fixtures 1/3 месяца и oversized | Локально подтверждено на fixture из 500 упражнений |
| 3 | Неизменный агрегат возвращает кеш без AI | unit/API + локальная DB | Локально подтверждено fingerprint- и cache-тестами |
| 4 | Автотесты не расходуют токены | mock provider + отсутствие live smoke | Подтверждено: только provider mocks, live smoke не запускается |
| 5 | База и обе функции выпущены из одного merge | GitHub Actions + release verification | Запланировано |

## Границы

- Формат готового отчёта и экран Progress не меняются; prompt только объясняет
  модели компактное представление входных данных.
- Production-тренировки, замеры, цели и сохранённые анализы не переписываются.
- Новые сервисы, провайдеры, автоматические retry и AI-repair не добавляются.
